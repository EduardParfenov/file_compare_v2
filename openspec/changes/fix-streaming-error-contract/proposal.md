## Why

Потоковые ИИ-маршруты (`/api/v1/analyze`, `/api/v1/ai-report-page`) не имеют рабочего контракта ошибок, хотя именно он ломается первым при недоступном vLLM.

Фактическое поведение сегодня:

- `services/vllm_client.py::stream_analysis` — async-генераторная функция: её тело (включая `await client.chat.completions.create(...)`) выполняется только при первом `__anext__`, то есть уже внутри тела `StreamingResponse`. Поэтому `try/except VllmClientError → HTTP 502` в `main.py::analyze` и `main.py::ai_report_page` для реальных отказов vLLM **не срабатывает**: соединение не устанавливается, ошибка возникает уже после отправки заголовков ответа, и клиент получает HTTP 200 с оборванным потоком вместо 502.
- Обрыв во время стрима (сбой генерации после первых чанков) поднимает исключение наружу из тела ответа: поток SSE обрывается без явного сигнала клиенту, частичный вывод теряется без объяснения.
- Фронтенд (`static/app.js`) обрабатывает только HTTP-статус ответа; событий SSE с полем `event:` не разбирает, поэтому даже появление кадра ошибки привело бы к выводу `[object Object]` в панель ИИ.
- Блок ошибок `#aiError` в `static/index.html` имеет Tailwind-класс `hidden`, а `static/app.js` управляет его видимостью через `ui-hidden`; в результате сообщение об ошибке не видно пользователю в любом случае (пересечение с пунктом P0.6 бэклога).
- Спецификация `pdf-hybrid-comparison` описывает HTTP 502 только для `/api/v1/ai-report-page` и не фиксирует контракт ошибок стриминга ни для одного из маршрутов.

Итог: при недоступном или зависшем vLLM пользователь получает пустую панель ИИ-аналитики без объяснения причины — пункт **P0.2** бэклога.

## What Changes

- **Бэкенд, маршруты `/api/v1/analyze` и `/api/v1/ai-report-page`:** соединение с vLLM устанавливается и первый фрагмент ответа читается **до** отправки заголовков ответа. Любой сбой до первого чанка приводит к HTTP 502 с понятным сообщением вместо HTTP 200 с пустым телом.
- **Бэкенд, обрыв во время стрима:** сбой генерации преобразуется в явный SSE-кадр `event: error` с полезной нагрузкой `data: {"error": "<сообщение>"}`, после чего поток закрывается штатно (ответ не обрывается на полуслове, частичный вывод сохраняется).
- **Бэкенд, заголовки SSE-ответа:** добавляются `Cache-Control: no-cache` и `X-Accel-Buffering: no`, чтобы реверс-прокси (Nginx) не буферизовал поток и не искажал моменты доставки кадров (часть пункта P1.3 бэклога).
- **Бэкенд, конфиденциальность сообщений об ошибках:** пользователю не раскрывается внутренний адрес эндпоинта vLLM; детали ошибки остаются в серверных логах (согласуется с уже действующим требованием к `/api/v1/health`).
- **Фронтенд, разбор SSE:** единый разбор потока, учитывающий поле `event:`; кадр `event: error` показывается пользователю как сообщение об ошибке, уже полученный частичный вывод не теряется, кнопка возвращается в доступное состояние.
- **Фронтенд, обрыв на уровне сети:** прерывание потока на стороне браузера (обрыв соединения, перезагрузка сервера) тоже даёт пользователю явное сообщение, а не пустой вывод.
- **Фронтенд, видимость сообщения об ошибке:** у `#aiError` остаётся единственный механизм скрытия — `ui-hidden` (класс `hidden` из `static/index.html` убирается), чтобы сообщение об ошибке реально отображалось. Это минимальная часть пункта P0.6 бэклога, необходимая для приёмки P0.2; остальные подпункты P0.6 остаются за backlog.
- **Тесты:** добавляются проверки async-генератора, падающего именно при итерации (сейчас мок бросает исключение синхронно при создании потока, из-за чего ветка 502 проверяется только формально), для обоих маршрутов: 502 до первого чанка, кадр `event: error` при сбое в середине потока, отсутствие кадра ошибки при успешном стриме; добавляется браузерный (Playwright) тест, что пользователь видит сообщение об ошибке.
- **Спецификация:** `pdf-hybrid-comparison` приводится в соответствие с фактическим контрактом ошибок потоковых маршрутов.
- **Бэклог:** пункт P0.2 закрывается этим change'ом; в пункте P1.3 отмечается, что часть (заголовки SSE) закрыта здесь, остальное (таймауты, keep-alive, устойчивость к зависшему vLLM) остаётся открытым.

Изменений, ломающих внешний контракт HTTP-маршрутов, нет: сигнатуры `POST /api/v1/analyze` и `POST /api/v1/ai-report-page`, состав полей запроса и MIME-тип ответа `text/event-stream` сохраняются.

## Capabilities

### New Capabilities

Нет. Новая пользовательская возможность не вводится — уточняется и дорабатывается контракт существующих потоковых маршрутов.

### Modified Capabilities

- `pdf-hybrid-comparison`: уточняется сценарий HTTP 502 в требовании «Кодирование изображения в Base64 перед отправкой в vLLM» (сбой ограничен случаем «до первого фрагмента»), добавляются требования к явному SSE-кадру ошибки, к корректному закрытию потока, к заголовкам SSE-ответа и к отображению ошибок на фронтенде.

## Impact

Затрагиваемые файлы (на этапе реализации):

- `main.py` — установка соединения до отправки ответа, кадр `event: error`, заголовки SSE-ответа, явное закрытие upstream-потока при отмене, маскирование внутренних сведений на границе ответа.
- `static/app.js` — единый разбор SSE с учётом поля `event:`, обработка сетевого обрыва потока, восстановление состояния кнопки.
- `static/index.html` — у `#aiError` остаётся только класс `ui-hidden`.
- `services/vllm_client.py` — сигнатуры публичных методов не меняются; ошибка пользователю описывается нейтральной фразой (без тела ответа vLLM, внутреннего адреса и ключа), детали уходят в серверный лог (см. `design.md`, D4).
- `tests/` — новые тесты на ошибки стриминга (бэкенд) и браузерный тест видимости ошибки.
- `openspec/specs/pdf-hybrid-comparison/spec.md` — дельта требований (применяется при синхронизации спек).
- `backlog.md` — закрытие P0.2 и уточнение статуса P1.3.

Новые зависимости не требуются. Публичный API и формат запросов не меняются; изменяется только поведение при ошибках.
