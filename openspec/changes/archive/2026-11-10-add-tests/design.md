## Context

Текущее состояние: в проекте нет папки `tests/` и нет тестового фреймворка в `requirements.txt` (`pytest` отсутствует). Приложение построено на FastAPI + uvicorn, использует `diff-match-patch` (движок diff), PyMuPDF (обработка PDF) и клиент vLLM (`openai.AsyncOpenAI`). Конфигурация читается через `os.getenv` с дефолтами (`config.py`, без внешних зависимостей типа pydantic-settings). Мотивация изменения — в `proposal.md` (раздел Why), не повторяется здесь.

## Goals / Non-Goals

**Goals:**
- Добавить unit-тесты, couvrantщие ядро приложения: `services/diff_engine.py`, `services/pdf_handler.py`, `config.py`, роуты `main.py` (`/api/v1/health`, `/api/v1/compare`).
- Обеспечить возможность запуска тестов без запущенного vLLM endpoint (ИИ-маршруты изолированы через моки).
- Добавить `pytest` в `requirements.txt` и `conftest.py` с фикстурами TestClient FastAPI.
- Тесты должны запускаться из виртуального окружения `.venv/` и не зависеть от пользовательских файлов в `input/`.

**Non-Goals:**
- Тестирование фронтенда (`static/app.js`, `static/index.html`) — не в объеме данного изменения.
- Интеграционное тестирование с реальным vLLM endpoint — требует внешней инфраструктуры.
- Тестирование отсканированных PDF через реальный рендер изображений в vLLM.

## Decisions

### 1. Фреймворк тестирования: pytest
**Обоснование:** де-факто стандарт для Python, поддерживает фикстуры и параметризацию, хорошо интегрируется с FastAPI (TestClient поставляется вместе с fastapi/starlette). Не требует добавления тяжелых зависимостей.
**Альтернативы:** `unittest` (в stdlib, но меньше возможностей и менее идиоматично для FastAPI). Отклонен.

### 2. HTTP-тестирование API: fastapi TestClient
**Обоснование:** входит в комплект fastapi (через starlette), не требует новой зависимости в `requirements.txt`. Позволяет тестировать роуты без запуска uvicorn.
**Альтернативы:** `httpx` с ASGI-транспортом (уже в зависимостях, но TestClient проще для синхронных тестов FastAPI). TestClient выбран как оптимальный по соотношению простота/зависимости.

### 3. Структура папки `tests/` (зеркалит исходный код)
```
tests/
  conftest.py              # фикстуры: TestClient, временные PDF-файлы
  test_config.py           # тесты Settings (дефолты, env-переменные)
  test_diff_engine.py      # тесты compute_diff / compute_diff_with_coords
  test_pdf_handler.py      # тесты extract_text_and_coords / render_page_to_png
  test_main.py             # тесты роутов /api/v1/health, /api/v1/compare
```
**Обоснование:** простая, предсказуемая навигация; каждый тестовый файл соответствует одному исходному модулю.

### 4. Изоляция ИИ-маршрутов от vLLM
**Обоснование:** тесты не должны зависеть от доступности внешнего vLLM endpoint. В `test_main.py` клиент vLLM мокируется (monkeypatch `services.vllm_client.vllm_client` / его методы), чтобы роуты `/api/v1/analyze` и `/api/v1/ai-report-page` возвращали 502 при недоступности и корректно проксировали SSE при мокированном ответе.

### 5. Фикстуры PDF
**Обоснование:** минимальные валидные PDF создаются внутри тестов через PyMuPDF (или берутся из фикстур в `tests/fixtures/`), чтобы не полагаться на пользовательские файлы из `input/`.

### 6. Зависимость `pytest`
**Обоснование:** добавить `pytest` в `requirements.txt` с зафиксированной версией (согласно п. 2 AGENTS.md, версии фиксируются точно). `httpx` уже присутствует и может использоваться при необходимости.

## Risks / Trade-offs

- [Тесты PDF require PyMuPDF в тестовом окружении] → `pymupdf` уже в `requirements.txt`, установится вместе с остальными зависимостями.
- [Мокирование vllm_client может скрыть регрессии в реальной интеграции] → компенсируется тем, что интеграция с vLLM проверяется вручную; тесты фокусируются на маршрутизации и обработке ошибок (502 при VllmClientError).
- [Временные файлы от UploadFile] → в тестах используются `tmp_path` pytest и TestClient, временные файлы очищаются автоматически.

## Migration Plan

1. Добавить `pytest` в `requirements.txt` с точной версией.
2. Создать папку `tests/` с `conftest.py` и тестовыми файлами.
3. Запустить `pytest` из `.venv/` и убедиться, что все тесты проходят.
4. Добавить запуск `pytest` в этап проверок PR (в соответствии с AGENTS.md, секция 10: проверки перед вливанием в `main`).
Откат: удалить папку `tests/` и строку `pytest` из `requirements.txt` — изменения не затрагивают исходный код приложения.
