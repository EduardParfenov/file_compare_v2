## Context

См. `proposal.md` — Why. Ниже — только техническое состояние, которое определяет подход.

Наблюдаемое сегодня поведение (проверено экспериментом на текущем коде, мок — настоящий async-генератор, падающий при итерации):

- `POST /api/v1/analyze` с ошибкой в середине генерации возвращает **HTTP 200**, `content-type: text/event-stream` и **пустое тело** — ни код ошибки, ни кадр ошибки, ни частичный вывод. При `raise_server_exceptions=True` TestClient бросает `ExceptionGroup`, в продакшене uvicorn обрывает chunked-ответ.
- `except VllmClientError → HTTP 502` в `main.py::analyze` и `main.py::ai_report_page` для реальных отказов недостижим: `services/vllm_client.py::stream_analysis` — async-генераторная функция, её тело выполняется при первом `__anext__`, то есть уже в теле `StreamingResponse`, после отправки заголовков. Тесты `tests/test_main.py` этого не ловят: мок `_MockVllmClient.stream_analysis` — обычная функция, бросающая исключение синхронно при создании потока, то есть проверяется ветка, недостижимая в проде.
- `services/vllm_client.py` оборачивает любое исключение (включая обрыв во время итерации) в `VllmClientError`, в тексте которого указан внутренний адрес эндпоинта (`{self.api_url}`) — при отдаче наружу он попадёт к пользователю.
- `static/app.js` дублирует разбор SSE в двух местах (`runAiAnalysis`, `generateAiPageReport`) и разбирает только строки `data: `, поле `event:` не учитывает.
- `#aiError` в `static/index.html` имеет Tailwind-класс `hidden`, а `static/app.js` управляет видимостью через `ui-hidden` (`display: none !important`) — снятие `ui-hidden` не делает элемент видимым.

Проверенные факты о семантике async-генераторов (нужны для решения D1):

- `await anext(gen)` на генераторе, который падает до первого `yield`, выбрасывает исключение вызывающему коду — значит, ошибку до первого чанка можно превратить в HTTP 502 на уровне маршрута.
- Генератор, завершившийся без единого `yield`, даёт `StopAsyncIteration` — это «пустой успешный поток», а не ошибка.
- Ошибка в середине генерации выбрасывается на следующем `anext()` — её можно поймать в обёртке потока.

## Goals / Non-Goals

**Goals:**

- Один понятный контракт ошибок для обоих потоковых маршрутов: сбой до первого чанка → HTTP 502; сбой во время стрима → кадр `event: error` и штатное закрытие потока.
- Пользователь всегда видит причину сбоя: в панели ИИ-аналитики, а не пустой вывод.
- Внутренний адрес эндпоинта ИИ-модели не покидает сервер.
- Тесты, воспроизводящие реальный сценарий (async-генератор, падающий при итерации), а не синхронный `raise` в моке.

**Non-Goals:**

- Таймауты, keep-alive и устойчивость к зависшему vLLM — пункт P1.3 бэклога (в этом change закрывается только часть с заголовками SSE).
- Смена формата кадров данных (`data: "<текст>"`) и формата запросов к маршрутам.
- Прочие подпункты P0.6 (сворачивание панели ИИ, единый стиль классов скрытия по всему UI) — затрагивается только видимость блока ошибки, без которой не выполняется приёмка P0.2.
- Рефакторинг `services/vllm_client.py` в части ролей/структуры сообщений (пункт P2.4).

## Decisions

### D1. Соединение с vLLM устанавливается до отправки заголовков ответа («прогрев» генератора)

Маршрут перед созданием `StreamingResponse` получает первый фрагмент из upstream-потока и буферизует его; остальные фрагменты отдаются генератором.

- **Выбрано:** оставить `services/vllm_client.py` без изменения сигнатур, в `main.py` добавить общий помощник, который создаёт async-итератор, делает `await anext()` и возвращает пару «итератор + первый фрагмент». Ошибка на этом шаге (включая `VllmClientError` из клиента) перехватывается в маршруте и превращается в HTTP 502.
- **Почему:** изменение минимально и не трогает публичный интерфейс клиента, описанный в `AGENTS.md` §6.3; обе фазы (до первого чанка / во время стрима) обрабатываются в одном месте — в `main.py`; тест на «падающий при итерации» мок покрывает ровно тот путь, который сегодня не работает.
- **Альтернатива A (отклонена):** превратить `VllmClient.stream_analysis` в корутину, возвращающую async-итератор, и открывать соединение в `await create(...)`. Плюс — заголовки уходят сразу после установления соединения, не дожидаясь первого токена. Минусы — меняется сигнатура метода и все места вызова/моки, дублируется логика открытия потока в клиенте; выигрыш по времени до заголовков неощутим для пользователя (он всё равно ждёт первый фрагмент).
- **Альтернатива B (отклонена):** отправить заголовки сразу, а ошибку до первого чанка сообщать кадром `event: error`. Проще, но нарушает требование «502 при сбое до первого чанка» и не даёт клиенту отличить «модель не ответила» от «поток оборвался».
- **Компромисс:** заголовки ответа уходят после первого токена модели, а не сразу после запроса. Для UX это неотличимо (пользователь всё равно ждёт первый фрагмент), но при зависшей модели запрос не вернётся — таймауты остаются в P1.3.

### D2. Формат кадра ошибки: `event: error` + `data: {"error": "<текст>"}`

- Кадр данных сохраняет текущий вид: `data: "<json-строка с текстом модели>"`. Существующий фронтенд и сторонние потребители продолжают работать без изменений.
- Ошибка передаётся именованным SSE-событием `error` с JSON-полезной нагрузкой `{"error": "<текст>"}`. Имя события — стандартный способ отличить ошибочный кадр от кадров данных (у данных тип по умолчанию `message`); ключ `error` в объекте оставляет возможность добавить код/тип ошибки позже.
- **Альтернатива (отклонена):** передавать ошибку только в теле `data:` (например, `{"error": ...}`) — тогда клиент обязан различать «текст модели» и «служебный объект» по форме значения, что хуже читается и легче ломается.

### D3. Ошибка во время стрима не обрывает HTTP-ответ

Обёртка потока в `main.py` перехватывает `VllmClientError` и любые неожиданные исключения, отдаёт кадр `event: error` и завершает генератор штатно. Исключение наружу не пробрасывается: иначе uvicorn оборвал бы соединение, и клиент получил бы обрезанный поток вместо кадра с причиной.

В блоке `finally` обёртка явно закрывает upstream-поток (`await asyncio.shield(events.aclose())`): при отмене запроса (обрыв соединения с клиентом) иначе соединение с vLLM удерживалось бы до сборки мусора — недетерминированно. `shield` нужен, чтобы уже висящая отмена задачи не помешала закрытию потока.

- **Альтернатива (отклонена):** пробросить исключение наружу и рассчитывать на код ответа 500 — статус ответа уже отправлен, пользователь получит обрыв без объяснения.

### D4. Внутренний адрес эндпоинта и детали сбоя не попадают к пользователю

Тексты ошибок `VllmClientError` сейчас содержат `self.api_url`, а исходное
исключение openai-клиента может содержать **тело ответа vLLM** (для
`APIStatusError` это `Error code: 500 - {...}`) — то есть внутренние пути,
хосты и ключи. Адрес и содержимое ответа сервера — сведения о внутренней
инфраструктуре (тот же принцип уже закреплён требованием к `/api/v1/health`).

- **Решение (два слоя):**
  1. `services/vllm_client.py` **не пересказывает** исходное исключение
     пользователю: функция `describe_error()` классифицирует сбой
     (таймаут / недоступность / ошибка ответа модели / непредвиденная
     ошибка) и возвращает короткий нейтральный текст. Полные детали
     (адрес эндпоинта, тело ответа, трассировка) уходят в серверный лог
     через `logger.exception`.
  2. На границе ответа (`main.py::_public_error_message`) текст ошибки
     дополнительно маскируется функцией `sanitize_error_text()`: заменяются
     полный URL, `host:port` и имя хоста, а также ключ доступа (длиной от
     8 символов, чтобы короткие значения не портили обычный текст).
- **Почему так, а не только санитизация:** замена URL по точному совпадению
  не спасает — тело ответа vLLM содержит произвольные внутренние сведения.
  Классификация устраняет сам источник утечки, маскирование на границе
  ответа защищает от утечки, если источник ошибки изменится.
- **Альтернатива (отклонена):** санитизировать URL регулярным выражением в
  `main.py` — хрупко (формат сообщения может измениться) и оставляет
  санитизацию в двух местах.

### D5. Фронтенд: один разбор потока SSE с учётом `event:`

Разбор потока выносится в общую функцию (например, `consumeSseStream(response, { onChunk, onError })`), которую используют и ИИ-анализ, и ИИ-отчёт по странице. Правила:

- кадр с `event: error` → текст ошибки из `data.error` передаётся в обработчик ошибки, вывод не дополняется этим кадром;
- кадр без `event:` (либо `event: message`) → `data` разбирается как раньше: JSON-строка → текст, не-JSON → как есть;
- обрыв на уровне сети (исключение при чтении потока) → сообщение пользователю «соединение прервано»;
- элемент управления запуском всегда возвращается в доступное состояние.

**Альтернатива (отклонена):** оставить разбор в двух местах и дописать проверку `event:` в каждое — дублирование, расхождение поведения двух маршрутов.

### D6. Видимость сообщения об ошибке

В `static/index.html` у `#aiError` убирается Tailwind-класс `hidden`; единственным механизмом скрытия остаётся `ui-hidden` (`display: none !important` в `static/styles.css`), которым уже управляет `static/app.js`.

- **Альтернатива (отклонена):** переключать Tailwind-класс `hidden` из JS — смешивает механизмы скрытия в разных местах кода (пункт P0.6 бэклога как раз про это).

### D7. Тесты

- **Backend, новый файл `tests/test_streaming_errors.py`:**
  - мок — настоящий async-генератор, падающий **до** первого `yield` → HTTP 502 на `/api/v1/analyze` и на `/api/v1/ai-report-page` (а не 200 с пустым телом);
  - мок — async-генератор, отдающий фрагмент и падающий после него → HTTP 200, тело содержит `event: error` и ранее переданный фрагмент, тело не содержит traceback и внутреннего адреса;
  - успешный стрим → в теле только кадры данных, кадра `event: error` нет;
  - заголовки SSE-ответа содержат `Cache-Control: no-cache` и `X-Accel-Buffering: no`.
- **Frontend, новый файл `tests/test_frontend_ai_stream_error.py`** (Playwright, по образцу `tests/test_frontend_upload.py`): поднять приложение в фоновом потоке, подменить `main.vllm_client` моком, падающим при итерации, сравнить два PDF, запустить ИИ-анализ и проверить, что `#aiError` видим (ненулевой `offsetHeight`/видим через `is_visible`) и содержит текст ошибки, а `#aiOutput` содержит частичный вывод. Тест помечается `skipif` при отсутствии браузера — как в существующем e2e-тесте; в CI Chromium устанавливается.
- **Альтернатива (отклонена):** unit-тест разбора SSE, портированный на Python. Он проверял бы копию логики, а не `static/app.js`; такой подход в бэклоге (P1.5) уже помечен как ложнозелёный.
- Существующие тесты `tests/test_main.py` дополняются сценарием «async-генератор, падающий при итерации», а мок `_MockVllmClient` приводится к поведению настоящего клиента (ошибка при итерации), чтобы тесты не закрепляли недостижимую ветку.

### D8. Обратная совместимость

Формат кадров данных и сигнатуры маршрутов не меняются; изменение атомарно (бэкенд и фронтенд в одном pull request). Старый фронтенд, получив кадр `event: error`, выведет его в панель как служебный объект — деградация только при одновременном обновлении бэкенда без фронтенда, что исключено порядком выкладки в одном PR.

## Risks / Trade-offs

- [Задержка заголовков ответа до первого токена модели] → пользователь не получает отклик раньше первого фрагмента; приемлемо, так как контент всё равно не отображается до первого чанка. Если понадобится индикатор «генерация идёт» — это отдельная задача фронтенда.
- [Зависшая модель → запрос висит без таймаута] → в зоне P1.3; в этом change фиксируется, что «прогрев» не усугубляет ситуацию по сравнению с текущим поведением (сейчас запрос тоже ждёт первый чанк, только без возможности вернуть 502).
- [Ошибка после отправки заголовков не может изменить код ответа] → пользователь получает 200 + кадр `event: error`; это осознанный компромисс стандарта SSE, зафиксированный в требованиях.
- [Утечка внутренних деталей через тексты ошибок] → адрес и исходное исключение остаются только в серверном логе; в ответе — нейтральный текст.
- [Проверка фронтенда требует браузера] → тест помечается `skipif` и пропускается локально без Chromium; в CI браузер устанавливается (шаг в `ci.yml` уже есть), поэтому проверка не выпадает из PR.
- [Изменение текста ошибок в `services/vllm_client.py`] → затронуты тесты, проверяющие текст исключения (в текущем наборе таких проверок нет; при появлении — правится вместе).

## Migration Plan

1. Порядок выкладки: бэкенд и фронтенд обновляются вместе (один pull request, один релиз), порядок внутри не важен — новый фронтенд понимает старый поток (кадров `event: error` просто не будет), новый бэкенд сможет отдать кадр `event: error` старому фронтенду, что даёт деградацию только при частичном обновлении.
2. Откат: revert pull request; совместимость снимков данных не требуется (миграции данных нет).

## Open Questions

- Нужен ли отдельный кадр завершения (`event: done`)? — Нет: конец потока однозначно означает завершение, дополнительный кадр усложнил бы контракт без выигрыша. Если позже понадобится различать «модель закончила» и «поток закрыт по таймауту», это будет отдельное требование.
- Значение `max_tokens`/лимиты размера запроса — вне рамок этого change (см. P0.5/P2.4).
