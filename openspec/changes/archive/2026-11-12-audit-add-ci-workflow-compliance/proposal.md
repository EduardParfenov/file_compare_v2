## Why

Последний архивный change `add-ci-workflow` развернул правила охраны ветки на стороне GitHub (ruleset `main` активен с 2026-11-12, список обхода пуст, обязательная status check — `pytest`), и сама техническая блокировка работает: pull request с красной проверкой слить нельзя. Но проверка проекта на соответствие правилам, установленным этим change'ом, показала, что оформление изменений отстаёт от факта: внутри архивного change'а два взаимоисключающих утверждения о порядке архивирования, сценарий спеки о запуске `pytest` из произвольного каталога не выполняется (проверено: bare `pytest` из `/tmp` — 21 ошибка сбора, код возврата 2; из подкаталога — 0 тестов, код 5), в `AGENTS.md` §10 два пункта с номером «5», а факт о настроенном ruleset записан в архивный `design.md` — в обход правила «любое изменение — в отдельной ветке и через pull request».

Расхождения нужно устранить сейчас, пока архивный change ещё не стал частью истории, которую читают как эталон, и пока правки документации (в частности, `README.md` с описанием ruleset) не закоммичены: незакоммиченное состояние документации опаснее отсутствия документации — оно выглядит как уже принятое решение.

## What Changes

- **Появляется аудит-отчёт** `openspec/changes/audit-add-ci-workflow-compliance/audit-report.md`: проверка последнего архивного change'а, изменённых файлов и GitHub-артефактов (pull request #8, прогоны CI, ruleset `main`) на соответствие правилам `AGENTS.md` §10/§11/§14 — с перечнем находок, доказательствами (команды, идентификаторы прогонов, фрагменты правил) и статусом каждой находки.
- **Фиксируется единый порядок операций над change'ом**: реализация → приёмка локально → создание pull request → подтверждение приёмки фактами на стороне GitHub → закрытие задач приёмки и архивирование change'а в том же pull request → слияние. Правило переносится в `AGENTS.md` §11 и §14, чтобы агент и человек соблюдали одну и ту же последовательность.
- **Устраняется противоречие внутри архивного change'а**: `design.md` (пункт 5 «Порядок внедрения») утверждает, что архивирование выполняется после слияния pull request, тогда как `tasks.md` 5.5 фиксирует, что архивирование выполнено до слияния, и фактически архив создан в коммите `c1df1c4` ветки `chore/add-ci-workflow` — до создания pull request #8 (12:54) и до слияния (12:59). Формулировки приводятся в соответствие с фактическим порядком, а метка «факт» сохраняется как датированная запись, чтобы расхождение было видно, а не замаскировано.
- **Сценарий спеки о работе `pytest` из произвольного каталога приводится в соответствие с поведением pytest**: требование «Команда запуска тестов не зависит от рабочего каталога» уточняется — из корня репозитория команда `pytest` собирает и выполняет тесты, из другого каталога то же достигается указанием пути к каталогу тестов; поведение bare-`pytest` из подкаталога фиксируется в спеке как штатное («тесты не найдены»), а поведение из постороннего каталога — в `README.md` как известное ограничение, чтобы сценарий был проверяемым, а не декларативным.
- **В спецификацию CI добавляются требования о защите основной ветки**: основная ветка защищена правилом репозитория (pull request обязателен, список обхода пуст, force-push и удаление ветки запрещены) и имя обязательной status check совпадает с именем job в workflow — иначе переименование job молча блокирует слияние для всех.
- **Документация приводится в фактическое состояние**: устраняется дубль номера «5» в `AGENTS.md` §10 (нумерация 1–7 сохраняется, чтобы не сломать исторические ссылки `§10.2`/`§10.5`/`§10.7` в архивных артефактах), уточняется оценка длительности прогона CI в `README.md` (фактические прогоны: 44 с, 49 с, 57 с — оценка «3–4 минуты на холодном кэше» не подтверждена), фиксируется в `backlog.md` пункт о неавтоматизированной проверке `openspec validate --specs --strict` в CI (вне объёма этого change).
- **Незакоммиченные правки** (`AGENTS.md`, `README.md`, `backlog.md`, архивный `design.md`) фиксируются в отдельной ветке и уходят через pull request — до сих пор они существуют только в рабочем дереве, что противоречит `AGENTS.md` §10.1–§10.2.

## Capabilities

### New Capabilities

- `change-lifecycle`: жизненный цикл change'а в проекте — приёмка подтверждается фактами, архивирование выполняется в составе pull request после подтверждения приёмки, архивные артефакты не переписываются задним числом, а новые факты о состоянии репозитория фиксируются в документации проекта и главных спецификациях.

### Modified Capabilities

- `continuous-integration`: уточняется требование «Команда запуска тестов не зависит от рабочего каталога» (сценарий приводится в соответствие с фактическим поведением pytest) и добавляются требования «Основная ветка защищена правилом репозитория» и «Имя обязательной проверки совпадает с job в CI».

## Impact

**Код приложения:** не затрагивается. `main.py`, `config.py`, `services/`, `static/` не меняются; продуктовое поведение приложения не меняется.

**Спецификации:**

- `openspec/specs/continuous-integration/spec.md` — обновляется по дельте этого change'а (уточнение сценария + два новых требования).
- `openspec/specs/change-lifecycle/spec.md` — новая capability; создаётся синхронизацией дельты при архивировании.

**Документация:**

- `AGENTS.md` — нумерация §10; §11 и §14 — канонический порядок операций над change'ом и правило неизменяемости архивных артефактов.
- `README.md` — уточнение длительности прогона CI; при необходимости — ссылка на канонический порядок операций.
- `backlog.md` — закрытие/уточнение пунктов, затронутых аудитом; новый пункт на проверку `openspec validate` в CI.

**Архивные артефакты:**

- `openspec/changes/archive/2026-11-11-add-ci-workflow/design.md` — устранение противоречия в пункте 5 «Порядок внедрения»; правка помечается как датированное уточнение.
- `openspec/changes/archive/2026-11-11-add-ci-workflow/tasks.md` — правка не требуется: формулировка 5.5 соответствует факту, приводить в соответствие нужно design.md.

**Тесты:** продуктовый код не меняется — новых функциональных тестов не требуется. Проверка `pytest` (59 тестов) должна остаться зелёной; проверка `openspec validate --specs --strict` — обязательная для этого change'а, поскольку меняются спецификации.

**Вне объёма:**

- Добавление шага `openspec validate --specs --strict` в `.github/workflows/ci.yml` — отдельная задача в `backlog.md` (решение владельца от 2026-11-12).
- Линтеры и форматтеры (`P2.11b`), лицензирование workflow, изменение состава проверок в CI.
- Перенос сведений о настройке репозитория на стороне GitHub в код (ruleset остаётся настройкой репозитория, как и задумано решением D7 последнего change'а).
