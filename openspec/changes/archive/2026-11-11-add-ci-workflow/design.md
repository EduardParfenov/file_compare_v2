## Context

Текущее состояние, которое определяет подход (мотивация — в `proposal.md`):

- В репозитории нет каталога `.github/`, нет ни одного workflow. Для открытого pull request `gh pr checks` сообщает «no checks reported».
- `AGENTS.md` §10.5 объявляет pull request пройденным после code review и успешного прохождения проверок (тесты, линтинг, сборка); §10.7 требует зелёного `pytest` перед созданием pull request. Сейчас это правило держится только на дисциплине автора.
- Набор тестов (59 штук) запускается только как `python -m pytest` **из корня проекта**. Консольный скрипт `pytest` падает при сборе с `ModuleNotFoundError: No module named 'main'` (`tests/conftest.py` импортирует `main`), потому что скрипт не добавляет рабочий каталог в `sys.path`, а `python -m` — добавляет. Из другого каталога падает и `python -m pytest`. Проверено фактически.
- Конфигурации pytest в репозитории нет (`pytest.ini`, `pyproject.toml`, `setup.cfg`, `tox.ini` отсутствуют), поэтому при bare-`pytest` из корня репозитория сборка рекурсивно обходит `.venv/`.
- Браузерный тест `tests/test_frontend_upload.py` требует Chromium. Без браузера он помечается как пропущенный (проверено: `58 passed, 1 skipped`, код выхода 0). С 2026-11-11 тест поднимает приложение сам — uvicorn в фоновом потоке на свободном порту, — и больше не требует внешнего сервера.
- Браузерный тест загружает страницу приложения, а страница подключает Tailwind, pdf.js и шрифты с внешних CDN. Тест требует, чтобы в консоли браузера не было ошибок, — значит, недоступность CDN приводит к падению теста, а не к его пропуску.
- Набор тестов не требует секретов: после `fix-runtime-bootstrap` он проходит без `.env` (проверено на копии проекта — 59 passed).
- Ограничения проекта: `AGENTS.md` §2 (Python 3.11), §10.2 (каждое изменение — в отдельной ветке), §10.5 (слияние только через PR на GitHub).

## Goals / Non-Goals

**Goals:**

- Один workflow, который на каждый pull request и на каждый push в основную ветку устанавливает зависимости, ставит браузер и прогоняет полный набор тестов.
- Ежедневная команда проверки, одинаковая локально и в CI, не зависящая от рабочего каталога.
- Никаких секретов в CI: проверка работает на дефолтной конфигурации.
- Документация, из которой понятно, что CI делает, что он требует от автора PR и как включить обязательную проверку.

**Non-Goals:**

- Линтеры и форматтеры (ruff, black, eslint, prettier) — отдельная задача; в этом change только тесты.
- Матрица операционных систем: проверка выполняется на одном публичном раннере `ubuntu-latest`.
- Branch protection как настройка репозитория: она включается в интерфейсе GitHub и не хранится в коде; в этом change только описать шаг.
- Локальный/оффлайн-пакет CDN-ресурсов (`P2.8` в `backlog.md`).
- Публикация артефактов тестов, отчёты о покрытии, матрица версий Python.

## Decisions

### D1. Конфигурация pytest выносится в `pytest.ini` с `pythonpath` и `testpaths`

**Решение.** Добавляется `pytest.ini`:

```ini
[pytest]
pythonpath = .
testpaths = tests
```

**Почему.** `pythonpath = .` добавляет корень репозитория в `sys.path` (путь разрешается относительно rootdir), поэтому и консольный скрипт `pytest`, и `python -m pytest` работают из любого каталога. Без этого описание проверки в CI вынужденно зависело бы от того, как именно вызвана команда, а правило `AGENTS.md` §10.7 («запустить `pytest` проходит без ошибок») оставалось бы ложным. `testpaths = tests` ограничивает сборку каталогом тестов: без него bare-`pytest` из корня рекурсивно обходит `.venv/`, что медленно и непредсказуемо.

**Уточнение по модели pytest (проверено на исходниках pytest 8.4.2).** `testpaths` применяются только при совпадении текущего каталога с `rootdir`; из другого каталога pytest ищет тесты рекурсивно от текущего каталога. Поэтому «любой рабочий каталог» означает: команда `pytest` с путём к каталогу тестов работает откуда угодно (проверено: 59 passed из `/tmp`), а bare-`pytest` без указания путей — из корня репозитория. Запуск bare-`pytest` из подкаталога проекта собирает 0 тестов (код возврата 5) — это штатное поведение pytest, а не дефект конфигурации; в CI рабочим каталогом является корень репозитория.

**Альтернативы.**

- *Вызывать в CI `python -m pytest`.* Работает, но оставляет расхождение с локальным запуском и не чинит противоречие §10.7: локальный `pytest` по-прежнему падает. Плюс привязка к способу вызова в описании CI.
- *Добавить `pyproject.toml`.* Работает, но проект не использует этот файл и не собирается как пакет; `pytest.ini` выражает намерение без лишней инфраструктуры.
- *Править `tests/conftest.py` (например, добавить `sys.path.insert`).* Маскирует проблему в одном месте: любой другой входной файл, импортирующий `main`, снова сломается.

### D2. Chromium устанавливается в CI: браузерный тест выполняется, а не пропускается

**Решение.** В workflow добавляется шаг установки браузера (`playwright install --with-deps chromium`), поэтому браузерный end-to-end тест реально выполняется.

**Почему.** Браузерный тест — единственная автоматическая проверка фронтенда: она ловит поломку разметки, обработчиков и обмена с бэкендом, которые не видны серверным тестам. Если в CI он молча пропускается, статус проверки создаёт ложное чувство покрытия: «зелёное» не означает, что страница работает. Решение зафиксировано владельцем проекта осознанно.

**Альтернативы.**

- *Не ставить браузер.* Быстрее (проверка ~1 мин вместо ~3–4), не зависит от PyPI-окружения и системных пакетов, но фронтенд в CI не проверяется вовсе.
- *Браузерный тест в отдельном job'е, не блокирующем слияние.* Снимает риск блокировки из-за внешних причин, но оставляет зелёный статус обязательной проверки без фронтенда и удваивает время проверки.
- *Vendoring CDN-ресурсов.* Устраняет зависимость от внешних сервисов, но это отдельная задача (`P2.8`).

### D3. Триггеры: pull request и push в основную ветку

**Решение.** Workflow запускается на `pull_request` (без ограничения по веткам — проверяется любой PR) и на `push` в `main`.

**Почему.** `pull_request` даёт проверку до слияния — это то, что требует §10.5. `push` в `main` подтверждает, что попавшее в основную ветку состояние действительно проходит проверку: PR мог быть смержен в обход или после других изменений в ветке. Ограничение по веткам для `pull_request` не задаётся — проверять нужно всё, что предлагается влить.

**Альтернативы.** *Только `pull_request`.* Проще, но не фиксирует состояние основной ветки. *`pull_request` + `push` по всем веткам.* Дублирует проверку для каждого push в рабочие ветки без практической пользы.

### D4. Зависимости устанавливаются из `requirements-dev.txt`

**Решение.** Шаг установки выполняет `pip install -r requirements-dev.txt` (файл подключает `requirements.txt` через `-r`).

**Почему.** Runtime-зависимости и инструменты тестирования разведены (это сделано в `fix-runtime-bootstrap`), и для проверки нужен весь набор: приложение (`main`, `services`, `pymupdf`, `openai`), `pytest` и `playwright`. Один файл — одно место, где объявлено, что нужно для запуска проверки; в workflow не дублируется список пакетов.

**Альтернативы.** *Устанавливать `requirements.txt` и `pytest`/`playwright` отдельными строками.* Расхождение с `requirements-dev.txt` — источник дрейфа: файл объявляет dev-зависимости, а CI ставит другие.

### D5. Python 3.11 и кэш pip

**Решение.** `actions/setup-python` с версией `3.11` (по `AGENTS.md` §2) и включённым кэшем pip, ключ которого — `requirements-dev.txt`.

**Почему.** Версия Python фиксирована правилами проекта: расхождение с локальным окружением означает, что проверка проверяет не то окружение, в котором идёт разработка. Кэш pip по файлу с зависимостями убирает из каждого прогона основную долю времени (скачивание wheels).

**Альтернативы.** *Матрица версий Python.* Для проекта с одним зафиксированным окружением — лишняя работа и лишние минуты; при изменении правил версии добавить легко.

### D6. Проверка не получает секретов

**Решение.** Workflow не определяет ни одной переменной окружения с секретами; `.env` в CI отсутствует, адрес эндпоинта ИИ-модели не передаётся.

**Почему.** Набор тестов этого не требует: он проходит на дефолтной конфигурации, а ИИ-роуты проверяются моками. Секреты в CI не нужны и не должны появляться: это убирает необходимость в секретах репозитория и риск их утечки через журналы проверки.

**Альтернативы.** *Передать `VLLM_API_URL` из secrets.* Не требуется тестами; привязывает проверку к инфраструктуре и делает её зависимой от настроек репозитория.

### D7. Обязательность проверки настраивается в интерфейсе GitHub и описывается в документации

**Решение.** Workflow только выполняет проверку. Требование «pull request нельзя слить с красной проверкой» настраивается как branch protection в интерфейсе GitHub (settings репозитория) и описывается в `README.md` как ручной шаг.

**Почему.** Настройки branch protection не хранятся в коде и не версионируются — их нельзя описать в файле репозитория и нельзя проверить автоматически. Единственное, что может сделать репозиторий, — дать саму проверку и объяснить, как её сделать обязательной.

**Альтернативы.** *Включить branch protection сразу.* Требует прав администратора репозитория и осознанного решения о блокировке слияния; кроме того, это действие вне репозитория, которое нельзя проверить тестом.

## Risks / Trade-offs

- **Проверка зависит от доступности внешних CDN** (Tailwind, pdf.js, Google Fonts): браузерный тест открывает страницу и требует отсутствия ошибок в консоли, поэтому недоступность CDN приводит к падению проверки. *Mitigation:* это тот же отказ, который сломает приложение у пользователя, — проверка его обнаруживает, а не маскирует. Если такие сбои окажутся частыми, браузерный тест выносится в отдельный неблокирующий job (альтернатива D2) либо CDN-ресурсы вендорируются (`P2.8`).

- **Установка Chromium с системными зависимостями занимает 1–2 минуты**, суммарная длительность проверки — порядка 3–4 минут. *Mitigation:* кэш pip; при превышении лимитов раннера — увеличение `timeout-minutes` или отказ от `--with-deps` в пользу предустановленного Chromium на образе.

- **Проверка может стать «красной по чужой причине»** и подорвать доверие к ней, если разработчики начнут обходить её. *Mitigation:* набор тестов не зависит от внешних сервисов, кроме CDN в браузерном тесте; журнал проверки показывает, на каком шаге произошёл сбой.

- **Появление `pytest.ini` меняет поведение локального запуска** для тех, кто полагался на `python -m pytest`: команда `pytest` теперь тоже работает, а `testpaths` ограничивает сборку каталогом `tests/` — при `pytest some_file.py` поведение не меняется. *Mitigation:* изменение описано в `README.md` и `AGENTS.md`; обратная совместимость сохранена (`python -m pytest` работает как раньше).

- **Публичные раннеры GitHub имеют ограничения по минутам и могут быть недоступны** при массовой нагрузке. *Mitigation:* для приватного репозитория учитывать лимиты бесплатного тарифа; при необходимости — self-hosted раннер.

## Migration Plan

1. Изменение не требует миграции данных и не меняет поведение приложения: затрагиваются только файлы CI и конфигурации тестов.
2. Порядок внедрения: `pytest.ini` → `.github/workflows/ci.yml` → документация → `backlog.md`.
3. Проверка перед merge: локальный `pytest` из корня репозитория и из произвольного каталога даёт одинаковый результат; в CI проверка отображается в pull request и завершается успешно.
4. После слияния: включить обязательную проверку (branch protection) в настройках репозитория на GitHub — ручной шаг, описанный в `README.md`.
5. **Архивирование change'а выполняется после слияния pull request** (решение владельца от 2026-11-11), а не до него, как было в предыдущих change'ах. Главная спека `openspec/specs/continuous-integration/spec.md` при этом создаётся уже в рамках pull request — отдельным действием синхронизации (`openspec sync add-ci-workflow`), — а само архивирование отложено до вливания. Пока change не заархивирован, он остаётся активным.
6. Откат: удаление `.github/workflows/ci.yml` и `pytest.ini` возвращает состояние репозитория к текущему; `pytest` снова требует запуска из корня проекта через `python -m pytest`.

## Open Questions

- Нужен ли линтер/форматтер в том же workflow (`ruff`, `black`) и в каком режиме — только отчёт или проверка с блокировкой. В рамках этого change не решается: добавление линтера требует сначала выбрать инструмент и зафиксировать его конфигурацию, иначе первая же проверка станет красной по стилю, а не по сути. Отложено до отдельного решения владельца.

- Нужна ли матрица операционных систем, раз проект не привязан к конкретной ОС. В рамках этого change не решается: одна проверка на `ubuntu-latest` уже даёт детерминированный сигнал, а матрица удваивает время проверки и число «красных» причин. Вопрос отложен до появления в проекте кода, чувствительного к ОС (например, работы с файловыми путями в Windows).
