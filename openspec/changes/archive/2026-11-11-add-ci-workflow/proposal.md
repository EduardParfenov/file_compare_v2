## Why

В репозитории нет ни одной автоматической проверки: каталога `.github/` не существует, поэтому `gh pr checks` для pull request сообщает «no checks reported». При этом `AGENTS.md` §10.5 объявляет pull request пройденным только после успешного прохождения проверок, а §10.7 требует зелёного `pytest` перед созданием pull request — сегодня это правило держится только на дисциплине автора, и красная ветка может быть влита незаметно.

Проверки можно было бы запускать и вручную, но ручной прогон не оставляет следа в pull request и не защищает от слияния без проверки. Кроме того, обнаружилось, что набор тестов не запускается стандартной командой `pytest` (консольный скрипт, в отличие от `python -m pytest`, не добавляет корень проекта в `sys.path` и падает с `ModuleNotFoundError: No module named 'main'`), то есть проверку нельзя было бы корректно описать в CI без дополнительной настройки.

## What Changes

- **Появляется CI-workflow** `.github/workflows/ci.yml`: запускается на каждый pull request и на каждый push в основную ветку, устанавливает зависимости разработки, ставит браузер для end-to-end теста и прогоняет полный набор тестов. Результат отображается в pull request как статус проверки.
- **Браузерный end-to-end тест выполняется, а не пропускается.** CI устанавливает Chromium, поэтому тест фронтенда (загрузка страницы, выбор двух PDF, запрос `/api/v1/compare`) реально прогоняется, а не помечается как пропущенный.
- **Появляется `pytest.ini`** с `pythonpath = .` и `testpaths = tests`. Это делает команду `pytest` работоспособной независимо от текущего рабочего каталога и ограничивает сборку тестов каталогом `tests/` (иначе bare-`pytest` из корня репозитория рекурсивно обходит `.venv/`).
- **Проверка не требует секретов и локальных файлов.** В CI нет `.env`, тесты проходят на дефолтных значениях конфигурации; адрес эндпоинта ИИ-модели в CI не передаётся и не нужен.
- **Документация:** в `README.md` и `AGENTS.md` появляется описание CI и того, как он соотносится с правилами §10.5/§10.7; в `backlog.md` закрывается пункт `P2.11`.

## Capabilities

### New Capabilities

- `continuous-integration`: автоматическая проверка изменений перед вливанием — запуск полного набора тестов на каждый pull request и push в основную ветку, независимость проверки от локального окружения разработчика и рабочего каталога, включение браузерного end-to-end теста.

### Modified Capabilities

Нет. Требования к продукту (`pdf-hybrid-comparison`, `configuration`) не меняются: CI не влияет на поведение приложения, его API и конфигурацию.

## Impact

**Новые файлы:**

- `.github/workflows/ci.yml` — CI-workflow.
- `pytest.ini` — конфигурация pytest (`pythonpath`, `testpaths`).

**Изменяемые файлы:**

- `README.md` — раздел о CI: что запускается, что требуется от PR, как включить обязательную проверку.
- `AGENTS.md` — §10.5/§10.7: уточнение, что проверки выполняются автоматически на каждом PR.
- `backlog.md` — пункт `P2.11` закрывается, декомпозиция приводится в соответствие.

**Продуктовый код:** не меняется. `main.py`, `config.py`, `services/`, `static/` не затрагиваются.

**Тесты:** существующий набор не меняется; CI лишь запускает его в новом окружении. Набор тестов должен оставаться зелёным без локального `.env` — это уже обеспечено правками `fix-runtime-bootstrap` и проверяется отдельным сценарием приёмки.

**Инфраструктура:** GitHub Actions на публичных раннерах `ubuntu-latest`; Python 3.11 (в соответствии с `AGENTS.md` §2); кэш pip по `requirements-dev.txt`. Секреты не используются.

**Вне объёма:** линтеры и форматтеры (ruff/black/eslint), матрица операционных систем, обязательная проверка (branch protection) как настройка репозитория на стороне GitHub, локальный/оффлайн-пакет CDN-ресурсов (`P2.8`).
