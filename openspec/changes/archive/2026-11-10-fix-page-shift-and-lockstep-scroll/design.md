## Context

Бэкенд (`services/pdf_handler.py`) уже возвращает слова с полями `global_char_start` / `global_char_end` — абсолютными смещениями от начала документа. Маршрут `/api/v1/compare` (`main.py`) передаёт эти координаты фронтенду вместе с результатом `compute_diff_with_coords`. Однако `services/diff_engine.py` не вычисляет символьные смещения для блоков diff: `DiffBlock` содержит только `op`, `text`, `html`. Фронтенд (`static/app.js`) вручную накапливает `block.text.length` в `mapWordsToOps`, чтобы сопоставить слова со страницами — это хрупко и ломается при сдвиге текста на новые страницы. Функция `syncScroll` в `static/app.js` использует пропорцию пикселей (`scrollTop / scrollMax`), что вызывает разъезд панелей при разной длине документов. См. мотивацию в `proposal.md` — Why.

## Goals / Non-Goals

**Goals:**
- Добавить `char_start` / `char_end` в `DiffBlock` и вычислять их в `compute_diff` для всех блоков (EQUAL, DELETE, INSERT) в обеих панелях.
- Упростить `mapWordsToOps` во фронтенде: использовать `char_start`/`char_end` блоков напрямую, без ручного накопления смещений и сброса указателя между страницами.
- Заменить `syncScroll` на якорную синхронизацию: целевая позиция определяется по ближайшему текстовому блоку (якорю), а не по пропорции пикселей; при прохождении через INSERT/DELETE противоположное окно показывает спейсер.
- Не менять внешний контракт API `/api/v1/compare`.

**Non-Goals:**
- Изменение сигнатуры или формата ответа `/api/v1/compare`.
- Изменение алгоритма diff-match-patch.
- Изменение `services/pdf_handler.py` или `services/vllm_client.py`.
- Конвертация PDF в Markdown или иные форматы.

## Decisions

**char_start/char_end в DiffBlock, вычисляемые в compute_diff.**
- Решение: добавить поля `char_start` и `char_end` в `DiffBlock`, вычисляемые как накопленная длина текста всех предыдущих блоков в рамках панели. `compute_diff` заполняет их для левой и правой панелей независимо.
- Обоснование: фронтенд получает абсолютную позицию каждого блока diff в символьном потоке панели, что устраняет необходимость вручную отслеживать смещения. Логика остаётся на бэкенде, где у неё есть полный контекст всех блоков.
- Альтернатива: оставить расчёт смещений во фронтенде (текущий подход) — отвергнуто, так как это дублирует логику и приводит к багам при сдвиге между страницами.

**Якорная синхронизация скроллинга вместо пропорциональной.**
- Решение: переписать `syncScroll` так, чтобы при скроллинге исходной панели целевая позиция целевой панели определялась по ближайшему блоку diff с той же операцией EQUAL, а не через `scrollTop / scrollMax`. При прохождении через блок INSERT/DELETE противоположная панель отображает спейсер (существующая логика `insertDiffSpacers`) и «замирает».
- Обоснование: привязка к текстовым якорям гарантирует, что неизменённые абзацы остаются на одной горизонтальной линии независимо от разницы в длине документов.
- Альтернатива: пропорциональный пиксельный скроллинг (существующий) — отвергнут, так как быстро рассинхронизируется при разном объёме текста.

**Не менять внешний контракт API.**
- Решение: `/api/v1/compare` сохраняет структуру ответа (`left_panel`, `right_panel`, `coords_left`, `coords_right`, `summary`, `meta`). Добавление `char_start`/`char_end` в блоки diff не ломает существующих потребителей.
- Обоснование: обратная совместимость позволяет逐步 внедрять исправление без ломки фронтенда или внешних интеграций.

## Risks / Trade-offs

- [Неточное определение высоты спейсера] → высота спейсера оценивается по вертикальному диапазону серии слов; возможна небольшая визуальная погрешность → компенсируется повторной синхронизацией при следующем EQUAL-блоке.
- [Сложность якорной синхронизации] → необходимо корректно определять «ближайший якорь» при скроллинге сквозь границы страниц → требует тестирования на многостраничных документах с вставками и удалениями.
- [Производительность на больших документах] → вычисление char_start/char_end линейно по количеству блоков, приемлемо для типичных PDF.

## Migration Plan

- Изменения локальны в `services/diff_engine.py` и `static/app.js`.
- Откат возможен в рамках одного коммита, так как внешний контракт API не меняется.
- Проверить на тестовых PDF с несколькими страницами и разным объёмом вставок/удалений.

## Open Questions

- Как обрабатывать пустые блоки diff (нулевая длина текста) при расчёте char_start/char_end — пропускать или присваивать то же смещение, что у предыдущего блока? (Не влияет на спецификации, решение можно принять при реализации.)
