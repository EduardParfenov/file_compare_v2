## Context

Текущее состояние, которое определяет подход (мотивация — в `proposal.md`):

- `config.py` при импорте вызывает `load_dotenv(override=True)` без указания пути. `python-dotenv` в этом случае ищет файл поиском вверх по дереву каталогов от кадра вызывающего модуля (`config.py`), то есть всегда от корня проекта и выше. Побочные эффекты: (а) в окружение процесса записываются значения `.env`; (б) `.env` из родительской директории подхватывается молча; (в) приоритет источников выражен только аргументом `override=True`.
- `Settings` — класс с атрибутами, вычисляемыми на момент создания класса (дефолты берутся из `os.getenv` в теле класса). Экземпляр `settings = Settings()` создаётся на импорте модуля; `services/vllm_client.py` создаёт синглтон `vllm_client` на импорте и читает `settings` в конструкторе.
- Тесты конфигурации вынуждены использовать `reload(config)`, чтобы повлиять на вычисление настроек. Из-за побочного эффекта в `os.environ` перезагрузка на машине с локальным `.env` подхватывает реальные значения проекта — 4 теста в `tests/test_config.py` падают.
- `main.py` монтирует статику как `StaticFiles(directory="static")` — путь разрешается относительно текущего рабочего каталога процесса.
- Корневого маршрута `GET /` нет; `/api/v1/health` возвращает `vllm_api_url` — внутренний адрес эндпоинта ИИ-модели.
- `requirements.txt` не содержит `python-multipart`, при этом `main.py` использует `File(...)` и `Form(...)`. Зависимость присутствует в локальном `.venv`, поэтому дефект не проявляется в тестах, но воспроизводится на чистой установке по файлу.
- Ограничения проекта: `AGENTS.md` §10.7 требует, чтобы перед созданием pull-request все тесты проходили; §4.2 запрещает жёстко заданные значения конфигурации в коде; §9 требует готовности к Docker и Nginx.

## Goals / Non-Goals

**Goals:**

- Одно правило приоритета, выраженное в коде: `.env` перекрывает окружение оболочки.
- Конфигурация, вычисляемая чисто: без записи в `os.environ`, без зависимости от того, откуда запущен процесс.
- Тесты конфигурации, дающие одинаковый результат на любой машине и не требующие `reload(config)`.
- Пути к `.env` и к `static/`, выведенные от расположения файлов приложения.
- Работоспособное приложение после чистой установки по `requirements.txt`.
- Зелёный `pytest` как побочный, но проверяемый результат.

**Non-Goals:**

- Контракт ошибок потоковой выдачи vLLM (`502` до первого чанка, `event: error`, заголовки для Nginx) — это отдельное изменение (`P0.2` в `backlog.md`).
- Валидация загружаемых файлов, лимиты размера и числа страниц (`P1.2`).
- Вынос блокирующих операций из event loop (`P1.1`).
- Изменение состава ответа `/api/v1/compare` и переработка `/compare` по объёму (`P1.6`).

## Decisions

### D1. Приоритет `.env` над оболочкой выражается слиянием словарей, а не мутацией окружения

**Решение.** Конфигурация вычисляется функцией, которая читает `.env` в словарь и сливает его поверх значений окружения:

```
merged = dict(os.environ)
merged.update({k: v for k, v in dotenv_values(env_file).items() if v is not None})
```

**Почему.** Приоритет виден в одной строке и не зависит от смысла аргумента `override=True` в сторонней библиотеке. Фильтрация `None` сохраняет поведение `python-dotenv`: ключ без знака `=` не затирает значение оболочки. Пустое значение (`KEY=`) перекрывает оболочку — как и при `override=True`.

**Альтернативы.**

- *Оставить `load_dotenv(override=True)` и починить только тесты.* Побочный эффект в `os.environ` сохраняется: любой импортирующий `config` код меняет процессное окружение, а тесты по-прежнему вынуждены делать `reload(config)`. Проблема «машино-зависимых» тестов чинится только наполовину — она возникает именно из-за мутации глобального состояния.
- *Отказаться от `python-dotenv` и писать свой парсер `.env`.* Отсутствует поддержка интерполяции `${VAR}` и комментариев, лишняя зависимость кода. Не рекомендуется.

### D2. Путь к `.env` — от `__file__`, без поиска вверх по дереву

**Решение.** `ENV_FILE = Path(__file__).resolve().parent / ".env"`. Файл читается, только если существует; иначе применяются дефолты.

**Почему.** `find_dotenv()` подхватывает `.env` из родительской директории — в этом проекте неожиданная конфигурация опаснее её отсутствия (тихо уехавший `VLLM_API_URL`). Явный путь делает поведение одинаковым при запуске из любого каталога.

**Альтернативы.** *Оставить `find_dotenv()`* — сохраняет риск случайного подхвата чужого `.env`. *Искать `.env` в CWD* — reintroduзирует зависимость от каталога запуска, от которой мы уходим.

### D3. `Settings` получает фабричный конструктор, `settings` остаётся единственным источником для приложения

**Решение.** `Settings` превращается в dataclass с полями и класс-методом `from_env(values)`, который принимает словарь значений и подставляет дефолты для отсутствующих ключей. На уровне модуля остаётся `settings = Settings.from_env(read_environment())`. Публичные точки доступа (`config.settings` в `main.py`, `services/vllm_client.py`) не меняются.

**Почему.** Сейчас значения настроек вычисляются в теле класса, то есть при импорте модуля, и единственный способ подменить их в тесте — `reload`. Фабрика отделяет «как получить значения» от «как их применить»: тест передаёт словарь явно и не трогает глобальное состояние.

**Альтернативы.**

- *Оставить класс как есть и чинить тесты через `monkeypatch` + `reload`.* Оставляет главный источник нестабильности: результат теста зависит от того, есть ли в корне проекта локальный `.env`. Проблема, ради которой затевался change, вернётся при следующем добавлении теста.
- *Сделать `settings` ленивым (property/getter).* Тогда каждое обращение перечитывает окружение, а синглтон `vllm_client` перестаёт фиксировать адрес на старте — это меняет семантику существующего кода шире, чем требуется.

### D4. Корневой маршрут отдаёт тот же документ, что и статический файл интерфейса

**Решение.** `GET /` возвращает `FileResponse` с `static/index.html`. Отдельный шаблон или редирект не вводятся.

**Почему.** Один источник правды для интерфейса: правки `index.html` сразу видны и на `/`, и на `/static/index.html`. Редирект на `/static/index.html` работал бы, но добавил бы лишний переход и оставлял бы вкладку с техническим путём.

**Альтернативы.** *Редирект `RedirectResponse`.* Короче в коде, но хуже для пользователя и для относительных ссылок. *Отдельная страница-обёртка.* Дублирование разметки.

### D5. В ответе `/api/v1/health` адрес заменяется признаком наличия настройки

**Решение.** Ответ: `{"status": "ok", "vllm_model": <имя модели>, "vllm_configured": <bool>}`. Поле `vllm_api_url` удаляется.

**Почему.** Внутренний адрес эндпоинта ИИ-модели — часть конфигурации инфраструктуры, а не диагностика работоспособности приложения. Признак `vllm_configured` отвечает на тот же вопрос диагностики («настроен ли ИИ-контур?»), не раскрывая адреса. Имя модели остаётся: оно не является адресом и уже опубликовано в `.env.example`.

**Альтернативы.** *Оставить адрес, но маскировать хост.* Маскировка даёт ложное чувство защищённости при полном раскрытии порта и внутреннего адреса — проще убрать. *Сделать поле опциональным через флаг конфигурации.* Добавляет ещё одну переменную окружения и два режима ответа; неоправданно.

### D6. `python-multipart` переезжает в `requirements.txt`, инструменты разработки — в `requirements-dev.txt`

**Решение.** `requirements.txt` получает `python-multipart` с зафиксированной версией (в локальном `.venv` установлена `0.0.33`). `pytest` и `playwright` переносятся в новый `requirements-dev.txt`; `requirements.txt` остаётся списком runtime-зависимостей приложения.

**Почему.** `requirements.txt` сейчас смешивает runtime и разработку (`pytest`), из-за чего production-установка тянет тестовый инструментарий, а `playwright` — не объявлен вовсе, хотя используется в тестах. Разделение делает чистую установку по `requirements.txt` работоспособной и воспроизводимой для разработки.

**Альтернативы.** *Оставить всё в одном файле.* Проще, но не разделяет «нужно для запуска» и «нужно для разработки»; дефект с `python-multipart` повторится для любой новой runtime-зависимости.

### D7. Изменения в спецификации выражаются как REMOVED + ADDED для требования о загрузке `.env`

**Решение.** Требование «Загрузка переменных окружения из файла .env» удаляется и заменяется требованием «Приоритет файла .env над переменными окружения оболочки».

**Почему.** Сценарий «Переменные окружения из оболочки приоритетнее .env» внутри старого требования имеет название, противоречащее собственному телу: тело утверждало приоритет `.env`. Исправить только название нельзя — валидатор требует сохранить имена сценариев в блоке `MODIFIED`, а молчаливый переимен означал бы либо потерю сценария при архивировании, либо perpetuating противоречия. `REMOVED` + `ADDED` — единственный способ выразить «это требование было сформулировано неверно и заменяется».

**Альтернативы.** *Оставить старое название сценария как есть.* Спека продолжает противоречить сама себе — ровно та болезнь, которую change лечит. *Оставить название, изменив тело.* То же самое: противоречие остаётся в главной спеке навсегда.

## Risks / Trade-offs

- **Значения из `.env` больше не попадают в `os.environ` процесса** → любой будущий код или сторонняя библиотека, ожидающая переменную в окружении, её не увидит. *Mitigation:* в проекте `os.environ` читает только `config.py` (проверено); при добавлении потребителя окружения он должен читать `config.settings`. Это осознанный размен: чистое чтение против скрытого глобального состояния.

- **Приоритет `.env` перекрывает переменные, переданные оркестратором** (`docker run -e VLLM_API_URL=...`), если `.env` окажется в образе. *Mitigation:* `.env` остаётся в `.gitignore` и не копируется в образ; правило «не встраивать `.env` в образ» фиксируется в `README.md`. Альтернативный режим (приоритет оболочки) сознательно отвергнут: для этого проекта `.env` — основной локальный конфиг, а инфраструктурные адреса задаются именно в нём.

- **Смена состава ответа `/api/v1/health`** ломает потребителя, читающего `vllm_api_url` (в проекте — тест `tests/test_main.py`). *Mitigation:* изменение описано в `proposal.md` и в дельте-спеке; тест обновляется в этом же change. Внешних потребителей у эндпоинта нет.

- **Отказ от `reload(config)` в тестах требует переписывания 4 тестов** → риск, что при переписывании ослабнут проверки. *Mitigation:* каждый переписанный тест получает явный вход (словарь значений или путь к файлу `.env` в `tmp_path`) и явное ожидаемое значение; добавляются тесты на приоритет, пустое значение, ключ без `=` и на отсутствие мутации `os.environ`.

- **Сохранение приоритета `.env` над оболочкой означает, что опечатка в `.env` «побеждает» корректно заданную переменную окружения** → конфигурация может оказаться не той, которую ожидал оператор. *Mitigation:* правило фиксируется явно в `AGENTS.md` и `README.md`; адрес ИИ-эндпоинта виден в `config.settings` при отладке, а проверка `vllm_configured` в `/api/v1/health` позволяет заметить отсутствие настройки.

## Migration Plan

1. Изменение не требует миграции данных: формат `.env` не меняется, схема API меняется только в составе ответа `/api/v1/health`.
2. Порядок внедрения: сначала `config.py` и `tests/test_config.py` (возвращает зелёный `pytest`), затем `main.py` (маршрут `GET /`, путь к статике, состав health), затем `requirements.txt` / `requirements-dev.txt`, затем документация (`AGENTS.md`, `README.md`).
3. Проверка перед merge: `pytest` проходит без ошибок на машине с локальным `.env` и на машине без него; приложение запускается из корня проекта и из произвольного каталога; `GET /` отдаёт интерфейс; `/api/v1/compare` принимает два PDF.
4. Откат: изменение несовместимо с прежним составом ответа `/api/v1/health` — при откате требуется вернуть прежний состав ответа (изменение изолировано в одном маршруте и одном файле тестов).

## Open Questions

- Следует ли выносить `python-dotenv` из runtime-зависимостей, если чтение `.env` перевести на собственный парсер ради отказа от побочных эффектов. В рамках этого change не решается: `dotenv_values` не имеет побочных эффектов и покрывает интерполяцию `${VAR}`, поэтому отдельная реализация парсера не нужна. Вопрос отложен до появления требований к формату `.env`, которых `python-dotenv` не покрывает.
