## Context

См. proposal.md — Why (мотивация). На момент этого change'а в репозитории уже есть:
- `.github/workflows/ci.yml` — job `pytest` на `pull_request` и `push` в `main`, установка зависимостей из `requirements-dev.txt`, установка Chromium для end-to-end теста, запуск `pytest -q`. Секреты не используются.
- ruleset `main` на GitHub (активен с 2026-11-12): обязательный PR, пустой список обхода, strict status check `pytest`, запрет force-push и удаления ветки.
- `backlog.md` пункты P2.11b (линтеры/форматтеры) и P2.14 (`openspec validate --specs --strict` в CI) отмечены как невыполненные.
- Аудит-отчёт `audit-add-ci-workflow-compliance` фиксирует находку N7: валидность артефактов OpenSpec не защищена автоматически.

Конвейер сейчас проверяет только функциональные тесты (`pytest`). Добавление линтеров/форматтеров и валидации OpenSpec не меняет продуктовый код, API и конфигурацию приложения — расширяет только набор проверок на стороне GitHub Actions.

## Goals / Non-Goals

**Goals:**
- Добавить в `.github/workflows/ci.yml` шаги запуска линтеров и форматтеров кода (Python и фронтенд) на каждом PR и push в `main`.
- Добавить в `.github/workflows/ci.yml` шаг `openspec validate --specs --strict` для валидации артефактов OpenSpec на каждом PR и push в `main`.
- Сохранить независимость конвейера от локального окружения: без секретов, без `.env`, без доступа к эндпоинту ИИ-модели.
- Обеспечить, чтобы непрохождение любого нового шага приводило к статусу «ошибка» проверки и блокировало слияние (через существующий strict status check).

**Non-Goals:**
- Менить продуктовый код (`main.py`, `config.py`, `services/`, `static/`).
- Менить тесты или добавлять новые функциональные тесты приложения.
- Менить главные спецификации под `openspec/specs/` (вне объёма этого change'а; дельта требований фиксируется в specs change'а).
- Настраивать линтеры/форматтеры как обязательные status checks в ruleset на стороне GitHub — это ручной шаг владельца репозитория, отдельная задача.
- Выбирать конкретные линтеры/форматтеры и их правила — оставить на этапе реализации (указаны как примеры в спеке).

## Decisions

### Добавить новые шаги в существующий job `pytest`, а не новый job

**Почему:** Конвейер и так запускает одну проверку с именем `pytest`, которая привязана к ruleset `main` как обязательная status check. Новый job с новым именем потребовал бы обновления ruleset (иначе слияние заблокируется, см. сценарий specs `continuous-integration` «Имя обязательной проверки совпадает с job в CI»). Расширение одного job не ломает существующую привязку.

**Альтернативы:** отдельный job `lint-and-validate` — отклонён, т. к. требует изменения ruleset `main` и ручного шага владельца репозитория.

### Линтеры/форматтеры и `openspec validate` запускать после установки зависимостей, перед `pytest`

**Почему:** Быстрая обратная связь — если код не проходит линтер или спецификации невалидны, нет смысла тратить время на установку браузера и прогон тестов. При этом оба шага используют уже установленные зависимости (`requirements-dev.txt` включает `pytest` и `playwright`; `openspec` устанавливается отдельно или уже доступен в окружении).

**Альтернативы:** запуск после `pytest` — отклонён, замедляет обратную связь при явных нарушениях оформления.

### `openspec validate --specs --strict` как обязательный шаг

**Почему:** без `--strict` невалидные артефакты могут пройти незамеченными; strict гарантирует, что любой дефект артефакта меняет код выхода команды и статус проверки.

**Альтернативы:** запуск без `--strict` — отклонён, не соответствует требованию specs.

## Risks / Trade-offs

- [Добавление линтеров может пометить как ошибки существующий код, который目前 проходит тесты] → ต้อง добавить etapas с `--fix` или отложить исправление существующих нарушений на отдельную итерацию, чтобы не блокировать все PR.
- [Открыт вопрос: какой набор линтеров/форматтеров и их правила] → оставить на этапе реализации; в specs заданы только требования к поведению конвейера, а не конкретные инструменты.
- [Открыт вопрос: как установить `openspec` в CI] → возможно, через `pip install openspec` или уже входящий в `requirements-dev.txt` пакет; уточнить на этапе реализации.
- [Увеличение времени прогона конвейера] → приемлемо; линтеры и валидация спецификаций работают быстрее браузерного теста.

## Open Questions

- Какие именно линтеры/форматтеры (ruff, black, eslint, prettier) и с какими правилами подключать — решается на этапе реализации.
- Как установить `openspec` CLI в окружении CI (отдельная зависимость или уже в `requirements-dev.txt`) — решается на этапе реализации.
- Нужно ли добавлять новые проверки как отдельные status checks в ruleset `main` помимо существующего `pytest` — решение владельца репозитория, вне объёма этого change'а.

## Migration Plan

Нет миграции пользовательских данных. Развёртывание ограничено коммитом изменений в `.github/workflows/ci.yml` в отдельной ветке и pull request; откат — обратный коммит workflow. Обязательные status checks на стороне GitHub настраиваются владельцем репозитория отдельно.
