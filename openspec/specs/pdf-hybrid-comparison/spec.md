## Purpose

Позволяет пользователям гибко сравнивать две версии PDF-документа: визуально — в формате Git Split Diff поверх оригинальной верстки страниц, и семантически — через ИИ-анализ изменений локальной VL-моделью Qwen3-VL-8B.

## Requirements

### Requirement: Двустороннее извлечение текста и координат из PDF

Система SHALL принимать два PDF-файла (исходную и измененную версии) и извлекать из каждого плоский текст sowie координаты слов и текстовых блоков (X, Y, ширина, высота) через PyMuPDF (`page.get_text("words")` / `page.get_text("blocks")`).

#### Scenario: Успешное извлечение текста и координат

- **WHEN** пользователь загружает два валидных PDF-файла
- **THEN** система возвращает текст обоих документов и для каждого текстового элемента координаты, пригодные для наложения прозрачного diff-слоя поверх страниц

#### Scenario: PDF без текстового слоя

- **WHEN** в одном из PDF отсутствует текстовый слой (отсканированный документ)
- **THEN** система возвращает ошибку или пустой текстовый результат с соответствующим уведомлением, а не ложные совпадения

### Requirement: Git Split Diff с разделением на левую и правую панели

Система SHALL вычислять diff с помощью алгоритма `diff-match-patch` и разделять операции EQUAL / INSERT / DELETE на два параллельных потока: для левой панели (исходная версия) только EQUAL и DELETE; для правой панели (измененная версия) только EQUAL и INSERT. Операции INSERT на левой панели и DELETE на правой панели SHALL игнорироваться.

#### Scenario: Удаленный текст отображается только слева

- **WHEN** фрагмент текста есть в исходной версии, но отсутствует в измененной (операция DELETE)
- **THEN** фрагмент отображается в левой панели и не отображается в правой панели

#### Scenario: Добавленный текст отображается только справа

- **WHEN** фрагмент текста есть в измененной версии, но отсутствует в исходной (операция INSERT)
- **THEN** фрагмент отображается в правой панели и не отображается в левой панели

#### Scenario: Неизмененный текст отображается в обеих панелях

- **WHEN** фрагмент текста одинаков в обеих версиях (операция EQUAL)
- **THEN** фрагмент отображается в левой и правой панели без подсветки изменений

### Requirement: Визуальная подложка страниц и прозрачный diff-слой

Система SHALL обеспечивать отображение каждой страницы PDF как полноценной графической подложки (через pdf.js в `<canvas>` на фронтенде) с наложенным поверх абсолютно позиционированным прозрачным HTML-слоем, в котором текстовые элементы размещены строго над своими визуальными положениями на странице согласно координатам из бэкенда. Каждое слово в ответе бэкенда SHALL содержать глобальные символьные индексы `global_char_start` и `global_char_end` — абсолютное смещение от самого начала документа. Каждый блок diff в `left_panel.blocks` и `right_panel.blocks` SHALL содержать сквозные символьные индексы `char_start` и `char_end` — абсолютное смещение от начала соответствующего текста панели, чтобы фронтенд мог сопоставлять глобальные блоки diff со словами без ручного накопления смещений между страницами.

#### Scenario: Текстовые элементы совпадают с подложкой страницы на любой странице

- **WHEN** фронтенд рендерит страницу через pdf.js и размещает текстовые элементы по координатам из ответа бэкенда на странице, отличной от первой
- **THEN** текстовые элементы попадают строго на места своего визуального отображения на странице, а подсветка diff корректно отражает операции ЕQUAL / DELETE / INSERT

#### Scenario: Глобальные символьные индексы слов

- **WHEN** бэкенд возвращает координаты слов для многостраничного документа
- **THEN** у каждого слова присутствуют поля `global_char_start` и `global_char_end`, задающие его абсолютное смещение в символьном потоке от начала документа

#### Scenario: Сквозные символьные индексы блоков diff

- **WHEN** бэкенд возвращает блоки diff для левой и правой панелей
- **THEN** каждый блок имеет поля `char_start` и `char_end`, задающие его абсолютное смещение в символьном потоке соответствующей панели, без сброса между страницами

### Requirement: Подсветка изменений на Diff-слое

Система SHALL подсвечивать на левой панели элементы операции DELETE полупрозрачным красным фоном с зачеркиванием, а на правой панели элементы операции INSERT — полупрозрачным зеленым фоном. Элементы INSERT на левой панели и DELETE на правой панели SHALL отсутствовать.

#### Scenario: Цветовая подсветка удалений и добавлений

- **WHEN** отображается результат diff
- **THEN** удаленные элементы слева имеют красную подсветку со зачеркиванием, добавленные элементы справа — зеленую подсветку без зачеркивания

### Requirement: Синхронный скроллинг с привязкой к текстовым якорям

Система SHALL обеспечивать синхронный (lock-step) скроллинг левого и правого окон, привязанный к текстовым блокам (якорям), а не к сырым пикселям. При прокрутке через блок вставки (INSERT) в Новом документе или блок удаления (DELETE) в Исходном документе противоположное окно SHALL временно показывать компенсирующее пустое пространство (spacer) соответствующей высоты, пока второе окно прокручивает изменённый фрагмент, чтобы неизмененные абзацы оставались строго друг напротив друга. Механизм синхронизации SHALL определять целевую позицию целевого окна по ближайшему текстовому якорю (блоку diff), а не по пропорции scrollHeight.

#### Scenario: Рассинхронизация при вставке большого абзаца

- **WHEN** в измененном документе вставлен большой абзац текста, отсутствующий в исходном
- **THEN** при скроллинге правым окном через этот абзац левое окно отображает пустой спейсер подходящей высоты, а после прохождения вставки окна снова синхронизируются по неизмененным блокам

#### Scenario: Рассинхронизация при удалении большого абзаца

- **WHEN** в исходном документе удален большой абзац текста, отсутствующий в измененном
- **THEN** при скроллинге левым окном через место удаления правое окно отображает пустой спейсер подходящей высоты, а после прохождения удаления окна снова синхронизируются по неизмененным блокам

#### Scenario: Якорная синхронизация вместо пропорциональной

- **WHEN** пользователь скроллит одну панель через неизмененный (EQUAL) фрагмент, а документы имеют разную длину из-за вставок/удалений
- **THEN** вторая панель позиционируется по соответствующему текстовому якорю (блоку EQUAL), а не по пропорции scrollHeight, и строки остаются выровненными по горизонтали

### Requirement: ИИ-анализ изменений через vLLM со стримингом

Система SHALL отправлять извлеченный текст и результаты diff в локальный vLLM endpoint (модель Qwen3-VL-8B) через асинхронный клиент OpenAI-совместимого API и передавать ответ пользователю в реальном времени через `StreamingResponse` (SSE) в боковую панель "AI Аналитика" в человекочитаемом формате.

#### Scenario: Потоковый вывод ИИ-саммари

- **WHEN** пользователь запускает сравнение двух версий PDF
- **THEN** боковая панель получает и отображает анализ изменений по частям по мере генерации моделью, без ожидания полного ответа

### Requirement: ИИ-отчет по текущей странице с визуальным контекстом

Система SHALL предоставлять в боковой панели кнопку "Сгенерировать ИИ-отчет по странице". При нажатии фронтенд SHALL делать снимок текущей видимой области страницы (canvas) или запрашивать у бэкенда рендер этой страницы в PNG через PyMuPDF и отправлять изображение в vLLM вместе с системным промптом для анализа изменений с учетом таблиц и сдвигов верстки.

#### Scenario: Анализ страницы с таблицами через VL-модель

- **WHEN** пользователь нажимает кнопку отчета по странице, на которой есть таблицы и сдвиги верстки
- **THEN** система отправляет изображение страницы и текстовый контекст в vLLM и отображает ИИ-разбор изменений с учетом визуальной верстки

### Requirement: Кодирование изображения в Base64 перед отправкой в vLLM

Эндпоинт `/api/v1/ai-report-page` SHALL принимать изображение страницы как загруженный файл (UploadFile), читать его байты, кодировать в строку Base64 и передавать в клиент vLLM вместе с системным промптом и MIME-типом, чтобы Qwen3-VL-8B могла получить изображение для анализа.

#### Scenario: Изображение конвертируется в Base64 перед вызовом vLLM

- **WHEN** клиент отправляет POST-запрос на `/api/v1/ai-report-page` с полем `image` (PNG/JPEG) и полем `system_prompt`
- **THEN** бэкенд читает байты изображения, кодирует их в строку Base64 и вызывает `stream_analysis_with_image` с параметрами `image_base64`, `image_mime_type` и `system_prompt`, возвращая потоковый ответ (StreamingResponse)

#### Scenario: Ошибка vLLM возвращается как HTTP 502

- **WHEN** vLLM endpoint недоступен или возвращает ошибку при обработке изображения
- **THEN** бэкенд возвращает HTTP 502 с понятным сообщением об ошибке, а пользователь может продолжить работу с обычным diff

### Requirement: Внешний контракт API `/api/v1/ai-report-page` не меняется

Эндпоинт `/api/v1/ai-report-page` SHALL по-прежнему принимать поля `image` (UploadFile) и `system_prompt` (Form) и возвращать `StreamingResponse` с MIME-типом `text/event-stream` после исправления.

#### Scenario: Контракт запроса сохраняется

- **WHEN** клиент вызывает `/api/v1/ai-report-page` с теми же полями, что до исправления
- **THEN** запрос принимается без изменений в сигнатуре endpoints, а ответ по-прежнему является потоковым SSE

### Requirement: Конфигурация через переменные окружения

Система SHALL читать все настройки (URL vLLM, имя модели Qwen3-VL, API-ключ, хост и порт FastAPI, настройки CORS) из переменных окружения (файл `.env`) с безопасным fallback на дефолтные значения при отсутствии `.env`.

#### Scenario: Запуск без файла .env

- **WHEN** приложение запускается в первый раз без файла `.env`
- **THEN** бэкенд инициализирует конфигурацию дефолтными значениями и продолжает работу без ошибок

### Requirement: Относительные пути AJAX-запросов на фронтенде

Система SHALL использовать только относительные пути (например, `/api/v1/compare`) для всех AJAX-запросов фронтенда, чтобы приложение работало за реверс-прокси (Nginx) и в Docker-контейнерах.

#### Scenario: Вызов API сравнения

- **WHEN** фронтенд отправляет файлы на бэкенд
- **THEN** запрос уходит на относительный путь `/api/v1/compare` без жестко заданного хоста

### Requirement: Изоляция окружения и игнорирование пользовательских файлов

Система SHALL устанавливать все зависимости в локальное виртуальное окружение `.venv/` в корне проекта, а папка `input/` с пользовательскими файлами SHALL игнорироваться системой контроля версий и документацией.

#### Scenario: Установка зависимостей в .venv

- **WHEN** разработчик активирует `.venv` и устанавливает зависимости из `requirements.txt`
- **THEN** все пакеты устанавливаются локально в `.venv/` без воздействия на системный Python
