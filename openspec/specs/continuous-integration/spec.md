# continuous-integration Specification

## Purpose

Позволяет проверять каждое изменение до его вливания в основную ветку автоматически: репозиторий получает проверку, запускаемую на каждый pull request и на каждый push в основную ветку, которая устанавливает объявленные зависимости и прогоняет полный набор тестов — включая браузерный end-to-end тест фронтенда.

## Requirements

### Requirement: Автоматическая проверка каждого pull request

Система SHALL содержать проверку, которая запускается автоматически на каждый pull request в репозиторий и выполняет установку зависимостей разработки и полный прогон тестов. Результат проверки SHALL отображаться в pull request как статус проверки, сопровождаемый журналом выполнения.

#### Scenario: Pull request открыт

- **WHEN** в репозиторий открыт pull request с изменениями
- **THEN** автоматическая проверка запускается, а в pull request отображается её статус и журнал выполнения

#### Scenario: Тесты не проходят

- **WHEN** прогон тестов в проверке завершается с ошибкой
- **THEN** проверка получает статус «ошибка», и pull request по правилам проекта не считается прошедшим проверку до устранения причин

#### Scenario: Изменения попадают в основную ветку

- **WHEN** изменения попадают в основную ветку
- **THEN** автоматическая проверка запускается на этом push, подтверждая, что попавшее в основную ветку состояние проходит проверку

### Requirement: Проверка охватывает браузерный end-to-end тест

Проверка SHALL обеспечивать наличие браузера, необходимого браузерному end-to-end тесту, чтобы проверка не завершалась пропуском этого теста.

#### Scenario: Браузерный тест выполняется, а не пропускается

- **WHEN** выполняется автоматическая проверка
- **THEN** браузерный end-to-end тест выполняется и его результат учитывается в статусе проверки, а не помечается как пропущенный

#### Scenario: Браузерный тест падает при регрессии фронтенда

- **WHEN** браузерный end-to-end тест обнаруживает ошибку на странице приложения
- **THEN** проверка получает статус «ошибка»

### Requirement: Проверка не зависит от локального окружения разработчика

Проверка SHALL выполняться в окружении, не содержащем локального файла `.env`, секретов и иных артефактов машины разработчика, и SHALL использовать только объявленные в репозитории зависимости.

#### Scenario: В окружении проверки нет файла .env

- **WHEN** выполняется автоматическая проверка
- **THEN** тесты проходят без файла `.env`, без переменных окружения с секретами и без доступа к эндпоинту ИИ-модели

#### Scenario: Набор тестов одинаков локально и в проверке

- **WHEN** тесты запускаются локально той же командой, что и в проверке
- **THEN** собирается и выполняется тот же набор тестов, что и в проверке

### Requirement: Команда запуска тестов не зависит от рабочего каталога

Тесты SHALL собираться и выполняться командой `pytest` из корня репозитория, а из любого другого рабочего каталога — той же командой с указанием пути к каталогу тестов, без ручной установки путей и без зависимости от того, откуда запущена команда.

#### Scenario: Запуск из корня репозитория

- **WHEN** выполняется команда `pytest` из корня репозитория
- **THEN** собираются и выполняются все тесты проекта без ошибки импорта

#### Scenario: Запуск из произвольного каталога

- **WHEN** выполняется команда `pytest` с указанием пути к каталогу тестов из каталога, отличного от корня репозитория
- **THEN** собираются и выполняются те же тесты проекта, что и при запуске из корня репозитория, без ошибки импорта

#### Scenario: Запуск из подкаталога проекта без указания путей

- **WHEN** выполняется команда `pytest` без указания путей из подкаталога корня репозитория
- **THEN** тесты не собираются, а команда завершается кодом «тесты не найдены», а не ошибкой сбора или ошибкой импорта

#### Scenario: Сбор ограничена каталогом тестов

- **WHEN** выполняется команда `pytest` из корня репозитория без указания путей
- **THEN** собираются только тесты проекта, а не содержимое виртуального окружения и других служебных каталогов

### Requirement: Основная ветка защищена правилом репозитория

Репозиторий SHALL содержать активное правило защиты основной ветки, которое запрещает изменение основной ветки в обход pull request, не допускает обхода правила владельцем репозитория и требует успешного прохождения обязательной проверки перед слиянием.

#### Scenario: Изменение попадает в основную ветку

- **WHEN** изменения попадают в основную ветку
- **THEN** это происходит только через pull request, в котором обязательная проверка завершилась успешно

#### Scenario: Попытка прямого push

- **WHEN** выполняется прямой push в основную ветку, в том числе владельцем репозитория
- **THEN** push отклоняется сервером, а правило не имеет списка обхода

#### Scenario: Обязательная проверка не пройдена

- **WHEN** в pull request обязательная проверка завершилась с ошибкой или ещё не запустилась
- **THEN** слияние pull request недоступно

#### Scenario: Описание правила в документации

- **WHEN** состояние правила защиты основной ветки описывается в документации проекта
- **THEN** описание соответствует фактическим настройкам репозитория и не утверждает, что защита действует, если она отключена

### Requirement: Имя обязательной проверки совпадает с job в CI

Имя проверки, выбранной обязательной в правиле защиты основной ветки, SHALL совпадать с именем job в CI, который выполняет набор тестов.

#### Scenario: Обязательная проверка привязана к существующему job

- **WHEN** правило защиты основной ветки требует проверку
- **THEN** в pull request отображается проверка с этим именем, и её результат определяет возможность слияния

#### Scenario: Job в CI переименован

- **WHEN** имя job в CI изменено без обновления правила защиты основной ветки
- **THEN** обязательная проверка не находится в pull request, и слияние остаётся заблокированным до синхронизации имени в правиле репозитория

### Requirement: Конвейер выполняет проверку линтеров и форматтеров

Система SHALL на каждый pull request и на каждый push в основную ветку запускать линтеры и форматтеры кода и учитывать их результат в статусе автоматической проверки.

#### Scenario: Линтеры и форматтеры проходят успешно

- **WHEN** в pull request всё оформлено в соответствии с правилами линтеров и форматтеров
- **THEN** шаг проверки стиля кода завершается успехом, и статус проверки в pull request позволяет слияние

#### Scenario: Линтеры или форматтеры обнаруживают нарушение

- **WHEN** в pull request есть код, не проходящий линтер или форматтер
- **THEN** шаг проверки стиля кода завершается с ошибкой, и pull request не считается прошедшим проверку до устранения нарушений

### Requirement: Конвейер валидирует артефакты OpenSpec

Система SHALL на каждый pull request и на каждый push в основную ветку запускать проверку валидности артефактов OpenSpec (`openspec validate --specs --strict`) и учитывать её результат в статусе автоматической проверки.

#### Scenario: Артефакты OpenSpec валидны

- **WHEN** все файлы proposal.md, specs/*.md, design.md, tasks.md change'а соответствуют схеме spec-driven
- **THEN** шаг `openspec validate --specs --strict` завершается успешно, и статус проверки позволяет слияние

#### Scenario: Артефакт OpenSpec невалиден

- **WHEN** хотя бы один артефакт change'а не соответствует схеме spec-driven
- **THEN** шаг `openspec validate --specs --strict` завершается с ошибкой, и pull request не считается прошедшим проверку до исправления артефактов
