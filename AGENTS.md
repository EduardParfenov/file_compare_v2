# AGENTS.md — правила проекта file-compare-v2

Этот файл описывает все правила, соглашения и требования проекта. Любой агент (и человек) должен следовать им при внесении изменений в код, документацию и спецификации.

---

## 1. Назначение проекта

Веб-приложение для гибридного сравнения двух версий PDF-документов:
- **Визуальное сравнение** в стиле Git Split Diff (две панели side-by-side поверх оригинальной верстки страниц).
- **ИИ-анализ изменений** через локальную мультимодальную модель Qwen3-VL-8B (vLLM) с потоковым выводом (streaming).

## 4. Окружение, конфигурация и безопасность

### 4.1 Виртуальное окружение (`.venv/`)
- Все зависимости устанавливаются в локальное виртуальное окружение `.venv/` в корне проекта.
- Создание:
  - Windows (PowerShell): `python -m venv .venv` и `.venv\Scripts\Activate.ps1`
  - Windows (CMD): `python -m venv .venv` и `.venv\Scripts\activate.bat`
  - Unix/macOS: `python3 -m venv .venv` и `source .venv/bin/activate`
- Установка: `pip install -r requirements.txt`
- `.venv/` **обязательно** игнорируется в `.gitignore`.

### 4.2 Переменные окружения (`.env`)
- Все настройки (URL и ключ vLLM, имя модели, хост/порт FastAPI, CORS) читаются из переменных окружения.
- `.env.example` — публичный шаблон с дефолтными/пустыми значениями.
- `.env` с реальными секретами создаётся пользователем локально: `cp .env.example .env`.
- `.env` **обязательно** игнорируется в `.gitignore`.
- Чтение настроек — только через `config.py` (`os.getenv` с безопасным fallback на дефолтные значения). Жестко заданные значения в коде запрещены.
- **Приоритет источников:** встроенные дефолты < переменные окружения оболочки < `.env`. Если переменная задана и в оболочке, и в `.env` — побеждает значение из `.env`.
- Путь к `.env` определяется от расположения `config.py` (`__file__`), а не от текущего рабочего каталога и не поиском вверх по дереву каталогов: `.env` из родительской директории **не используется**.
- Чтение `.env` **не изменяет** переменные окружения текущего процесса (`os.environ` остаётся неизменным).
- Пустое значение в `.env` (`KEY=`) перекрывает значение оболочки; ключ без знака `=` игнорируется (значение оболочки сохраняется).

### 4.3 Папка `input/`
- Содержит дополнительные пользовательские файлы (не PDF-файлы для сравнения).
- **Не является частью кода проекта.**
- Игнорируется в `.gitignore` и упомянута в `README.md`.

## 5. Конфигурация бэкенда (`config.py`)

- `Settings` — dataclass с полями настроек; настройки собираются фабричным методом `Settings.from_env(values)`, подставляющим дефолты для отсутствующих ключей.
- `read_environment(env_file=ENV_FILE, base=None)` — чистая функция: читает `.env` (путь от `__file__`) и сливает его значения поверх окружения оболочки. Побочных эффектов нет.
- Экземпляр `settings = Settings.from_env(read_environment())` — единственная точка доступа во всём приложении.
- При отсутствии `.env` приложение должно стартовать без ошибок, используя дефолты.
- Приоритет источников: дефолты < окружение оболочки < `.env` (см. §4.2).
- Ключи:
  - `VLLM_API_URL` (дефолт: `http://localhost:8000/v1`)
  - `VLLM_MODEL_NAME` (дефолт: `qwen3-vl-8b`)
  - `VLLM_API_KEY` (дефолт: `""`)
  - `FASTAPI_HOST` (дефолт: `0.0.0.0`)
  - `FASTAPI_PORT` (дефолт: `8000`)
  - `CORS_ORIGINS` (дефолт: `"*"`)
- Поле `settings.vllm_configured` — признак того, что адрес эндпоинта ИИ-модели задан явно (в оболочке или в `.env`), а не взят из дефолта. Используется в `/api/v1/health`, который **не раскрывает** внутренний адрес эндпоинта.

## 6. Бэкенд: сервисы

### 6.1 `services/pdf_handler.py`
- `extract_text_and_coords(pdf_path)` — плоский текст + координаты слов/блоков через `page.get_text("words")` / `page.get_text("blocks")` (X, Y, ширина, высота).
- `render_page_to_png(pdf_path, page_number)` — рендер страницы в байты PNG для ИИ-отчета по странице.
- Ошибка `PdfHandlerError` при отсутствии текстового слоя (отсканированный PDF) — возвращать понятное уведомление, а не ложные совпадения.

### 6.2 `services/diff_engine.py`
- `compute_diff(text_a, text_b)` — diff через `diff-match-patch`.
- Левая панель (исходная версия): только `EQUAL` и `DELETE`. `DELETE` подсвечивается `<span class="bg-red-500/30 line-through">`.
- Правая панель (измененная версия): только `EQUAL` и `INSERT`. `INSERT` подсвечивается `<span class="bg-green-500/30">`.
- `INSERT` на левой панели и `DELETE` на правой панели **запрещены** (игнорируются).
- Возврат JSON с отдельными `left_panel` / `right_panel` (blocks + html) и координатами (`coords_left` / `coords_right`).

### 6.3 `services/vllm_client.py`
- `VllmClient` на базе `openai.AsyncOpenAI`, настроенный на эндпоинт vLLM из `config.settings`.
- `stream_analysis(prompt)` — потоковый текстовый ответ (SSE).
- `stream_analysis_with_image(system_prompt, image_base64, image_mime_type)` — потоковый визуальный анализ страницы (Qwen3-VL).
- При недоступности vLLM — выбрасывать `VllmClientError`, бэкенд возвращает HTTP 502 с понятной ошибкой; пользователь может продолжить работу с обычным diff.

### 6.4 `main.py`
- FastAPI-приложение с CORS (настройка из `CORS_ORIGINS`).
- Роуты (все относительные, готово к Nginx/Docker):
  - `GET /api/v1/health` — проверка работоспособности.
  - `POST /api/v1/compare` — прием двух PDF, вызов `pdf_handler` + `diff_engine`, возврат JSON_diff.
  - `POST /api/v1/analyze` — потоковый ИИ-анализ изменений (StreamingResponse / SSE).
  - `POST /api/v1/ai-report-page` — ИИ-отчет по странице: изображение + системный промпт → vLLM → потоковый ответ.
- Статика раздается из `static/` через `/static`.
- Нет жестко заданных хостов во фронтенд-запросах.

## 7. Фронтенд (`static/`)

### 7.1 `static/index.html`
- Два окна сравнения side-by-side (оригинал слева, новая версия справа).
- Сворачиваемая боковая панель "AI Аналитика".
- Подключение TailwindCSS через CDN и pdf.js через CDN.
- Относительные пути для всех AJAX-запросов (`/api/v1/...`).

### 7.2 `static/app.js`
- Загрузка двух PDF-файлов, отправка на `/api/v1/compare`.
- Рендер страниц через pdf.js в `<canvas>` (визуальная подложка).
- Прозрачный абсолютно позиционированный HTML-слой с текстовыми элементами (`<span class="diff-word">`) строго над своими координатами (PyMuPDF).
- Подсветка: удаленные (красный, зачеркивание) слева, добавленные (зеленый) справа.
- Умный синхронный скроллинг (lock-step) с привязкой к текстовым якорям (блокам), а не к пикселям.
- Боковая панель ИИ-аналитики со стримингом ответа (SSE).
- Кнопка "Сгенерировать ИИ-отчет по странице" — снимок текущей видимой области canvas → `/api/v1/ai-report-page` → vLLM.

### 7.3 `static/styles.css`
- Кастомные стили для diff-слоя, подсветки (`--diff-delete-bg`, `--diff-insert-bg`), компенсирующего пространства при замирании окна, полосы прокрутки, анимации вывода ИИ.

## 8. Требования к UI/UX (Git Split Diff + Side-by-Side Canvas)

- Нет конвертации PDF в Markdown. Отображение идет поверх оригинальной верстки страниц (pdf.js + `<canvas>`).
- Каждая страница PDF — полноценный графический объект (canvas).
- Координаты текстовых блоков/слов извлекаются бэкендом через PyMuPDF и передаются фронтенду.
- Синхронный скроллинг привязан к текстовым якорям. При добавленном блоке в Новом документе левое окно замирает (или показывает компенсирующее пустое пространство) до прохождения вставки.
- Боковая панель ИИ-аналитики с потоковым выводом и кнопкой отчета по странице с визуальным контекстом.

## 10. Правила ветвления и pull-request (обязательно для всего проекта)

**Это правило зафиксировано для всего проекта и не подлежит изменению без согласия команды.**

1. **Не коммитить напрямую в `main`.** Ветка `main` защищена — вливание в неё возможно только через pull-request. Правило обеспечено технически: ruleset `main` в GitHub (настроен 2026-11-12) запрещает прямой push в `main` — в том числе для владельца, — а также force-push и удаление ветки; слияние возможно только через pull request с зелёной проверкой `pytest`.
2. **Каждое изменение — в новую ветку.** Создавайте отдельную ветку от `main` для каждой задачи/фичи/исправления (например, `feature/...`, `fix/...`, `chore/...`).
3. **Pull-request обязателен.** Перед вливанием в `main` необходимо создать pull-request из рабочей ветки в `main`.
4. **PR оформляется только на GitHub.** Локальное слияние ветки в `main` через `git merge` вместо GitHub PR запрещено. PR создаётся через GitHub веб-интерфейс (`github.com/<user>/file-compare-v2/pulls`) или GitHub CLI (`gh pr create`). Ревью, approbation и слияние проходят через GitHub (кнопка "Merge pull request").
5. **Вливание только после прохождения PR.** PR считается пройденным после проверки кода (code review) и успешного прохождения проверок (тесты, линтинг, сборка). Вливание в `main` допускается только после одобрения PR. Проверки (тесты) выполняются автоматически на каждом pull request — workflow `.github/workflows/ci.yml` запускает полный набор тестов и отображает свой статус в pull request; решение о слиянии принимается только после того, как этот статус станет зелёным. (Проверка `pytest` выбрана обязательной в ruleset `main`: pull request с красным или ещё не запустившимся статусом слить нельзя — блокировка техническая, а не только по настоящему правилу.)

   **Удаление рабочей ветки.** После успешного вливания PR в `main` рабочая ветка **обязательно удаляется** (локально и на удалённом сервере).
6. **Имя ветки.** Используйте понятные имена: `feature/<задача>`, `fix/<задача>`, `docs/<задача>`, `chore/<задача>`.

7. **Тесты при любой правке кода.** При любом изменении исходного кода (`main.py`, `services/`, `static/app.js` и т.п.) необходимо добавить или обновить соответствующие тесты в папке `tests/` и убедиться, что все тесты зелёные (`pytest` проходит без ошибок), прежде чем создавать pull-request. Изменение без тестов не считается завершённым. Локальный прогон `pytest` перед созданием pull-request обязателен: он остаётся страховкой от «красного» CI, но проверку в pull request пропустить нельзя — она выполняется автоматически на каждом PR.

Пример рабочего процесса:
```bash
git checkout main
git pull origin main
git checkout -b feature/新功能
# ... изменения ...
git add -A
git commit -m "Описание изменений"
git push origin feature/новый-функционал
# Создать PR в main, пройти ревью и проверки
# После вливания:
git checkout main
git pull origin main
git branch -d feature/новый-функционал
git push origin --delete feature/новый-функционал
```

## 11. Планирование изменений (OpenSpec)

- Planning-артефакты хранятся в `openspec/changes/<имя-изменения>/`.
- Схема: `spec-driven` — `proposal.md` → `specs/<capability-path>/spec.md` → `design.md` → `tasks.md`.
- Спецификации описывают **WHAT** (поведение, требования, сценарии), а не реализацию.
- `design.md` описывает **HOW** (архитектура, решения, риски).
- `tasks.md` — чек-лист реализации с чекбоксами `- [ ]` / `- [x]`.

**Канонический порядок операций над change'ом:**

1. Реализация в отдельной ветке (§10.2).
2. Приёмка локально: `pytest` проходит без ошибок (§10.7).
3. Создание pull request в `main` (§10.3–§10.4).
4. Подтверждение приёмки фактами на стороне GitHub: идентификатор pull request и прогон проверки. Задачи приёмки в `tasks.md` закрываются **только** после фиксации проверяемого факта.
5. Закрытие задач приёмки и архивирование change'а (`openspec/changes/archive/...`) — в том же pull request, после подтверждения приёмки.
6. Слияние pull request на GitHub (§10.5).

**Неизменяемость архивных артефактов:**

- Архивные артефакты не дополняются новыми фактами после архивирования: новые сведения о состоянии репозитория (например, о настройках на стороне GitHub) фиксируются в `README.md`, `backlog.md` и главных спецификациях.
- Единственное исключение — исправление фактического противоречия в архивном артефакте: правка помечается **датированным уточнением** с указанием причины и ссылки на отчёт о проверке.
- Требования этого раздела зафиксированы в capability `change-lifecycle` (`openspec/specs/change-lifecycle/spec.md`); при расхождении правил и спецификации источником истины считается спецификация, а правила приводятся к ней в том же изменении.

## 12. Проверка и приемка

- Приложение запускается через `uvicorn main:app` (с дефолтным конфигом без `.env`).
- `/api/v1/health` должен возвращать `{"status": "ok", ...}`.
- `/api/v1/compare` должен возвращать JSON с отдельными `left_panel` / `right_panel` и координатами.
- ИИ-маршруты (`/api/v1/analyze`, `/api/v1/ai-report-page`) требуют доступного vLLM endpoint; при недоступности — понятная ошибка HTTP 502.

## 14. Правила взаимодействия с агентом (обязательно)

**Общий принцип:** агент может выполнять любые действия в проекте (включая команды git: создание и переключение веток, `git add`, `git commit`, `git push` и другие), **но обязан перед каждым таким действием запрашивать явное разрешение пользователя**, чётко описывая, что именно будет сделано. Агент **не работает с git и не выполняет другие изменяющие действия самостоятельно, без ведома пользователя**. Разрешение даётся на конкретное действие (или явно оговоренный набор действий) и не переносится автоматически на следующие шаги.

1. **Работа с git — только с разрешения пользователя.** Перед выполнением любой git-команды, изменяющей состояние репозитория или удалённых веток (создание/удаление ветки, `add`, `commit`, `push`, `merge`, `rebase`, `tag` и т.п.), агент сообщает планируемую команду/действие и запрашивает явное разрешение. Read-only команды git (`status`, `log`, `diff`, `show` и т.п.) агент может выполнять для анализа без отдельного подтверждения, если это не раскрывает лишний контекст сверх необходимого.
2. **OpenSpec-артефакты — только по подтверждению.** Файлы `proposal.md`, `specs/**/spec.md`, `design.md`, `tasks.md`, `.openspec.yaml` создаются/редактируются через команды `openspec` (`new change`, `instructions`, `status`, `apply` и т.п.) и только после подтверждения пользователя на каждый артефакт/шаг.
3. **Шаги планирования — без самостоятельных переходов.** Переход от одного артефакта к другому (`proposal` → `specs` → `design` → `tasks` → `apply`) возможен только после прямого согласия пользователя.
4. **Канонический порядок операций — из §11.** Приёмка, архивирование и слияние выполняются в порядке, зафиксированном в §11: подтверждение приёмки фактами → закрытие задач приёмки и архивирование change'а в том же pull request → слияние. Архивирование выполняется только после фиксации проверяемого факта приёмки; архивные артефакты не переписываются, кроме датированного уточнения с указанием причины.

**Все изменения в кодовой базе проходят через следующий порядок:**

1. Обсуждение и планирование в explore mode (без записи кода).
2. Пользователь даёт подтверждение на объём изменений.
3. Агент создаёт OpenSpec-изменение через `openspec new change` и заполняет артефакты только по мере подтверждения пользователя.
4. Реализация кода только после того, как все артефакты OpenSpec подтверждены пользователем.
5. Тесты добавляются вместе с кодом (см. п. 7 раздела 10).
6. Коммит, создание ветки, push и оформление PR выполняются только после явного разрешения пользователя (агент может выполнить эти действия сам, если получил такое разрешение на конкретный шаг).

## 15. Язык ответа (обязательно)

**Агент всегда отвечает на русском языке.** Все ответы, комментарии к коду, сообщения о прогрессе и иные тексты, генерируемые агентом, пишутся на русском языке без исключений.
