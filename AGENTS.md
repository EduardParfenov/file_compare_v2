# AGENTS.md — правила проекта file-compare-v2

Этот файл описывает все правила, соглашения и требования проекта. Любой агент (и человек) должен следовать им при внесении изменений в код, документацию и спецификации.

---

## 1. Назначение проекта

Веб-приложение для гибридного сравнения двух версий PDF-документов:
- **Визуальное сравнение** в стиле Git Split Diff (две панели side-by-side поверх оригинальной верстки страниц).
- **ИИ-анализ изменений** через локальную мультимодальную модель Qwen3-VL-8B (vLLM) с потоковым выводом (streaming).

## 4. Окружение, конфигурация и безопасность

### 4.1 Виртуальное окружение (`.venv/`)
- Все зависимости устанавливаются в локальное виртуальное окружение `.venv/` в корне проекта.
- Создание:
  - Windows (PowerShell): `python -m venv .venv` и `.venv\Scripts\Activate.ps1`
  - Windows (CMD): `python -m venv .venv` и `.venv\Scripts\activate.bat`
  - Unix/macOS: `python3 -m venv .venv` и `source .venv/bin/activate`
- Установка: `pip install -r requirements.txt`
- `.venv/` **обязательно** игнорируется в `.gitignore`.

### 4.2 Переменные окружения (`.env`)
- Все настройки (URL и ключ vLLM, имя модели, хост/порт FastAPI, CORS) читаются из переменных окружения.
- `.env.example` — публичный шаблон с дефолтными/пустыми значениями.
- `.env` с реальными секретами создаётся пользователем локально: `cp .env.example .env`.
- `.env` **обязательно** игнорируется в `.gitignore`.
- Чтение настроек — только через `config.py` (`os.getenv` с безопасным fallback на дефолтные значения). Жестко заданные значения в коде запрещены.

### 4.3 Папка `input/`
- Содержит пользовательские PDF-файлы для сравнения.
- **Не является частью кода проекта.**
- Игнорируется в `.gitignore` и упомянута в `README.md`.

## 5. Конфигурация бэкенда (`config.py`)

- Класс `Settings` загружает все параметры через `os.getenv` с дефолтными значениями.
- Экземпляр `settings = Settings()` используется во всём приложении.
- При отсутствии `.env` приложение должно стартовать без ошибок, используя дефолты.
- Ключи:
  - `VLLM_API_URL` (дефолт: `http://localhost:8000/v1`)
  - `VLLM_MODEL_NAME` (дефолт: `qwen3-vl-8b`)
  - `VLLM_API_KEY` (дефолт: `""`)
  - `FASTAPI_HOST` (дефолт: `0.0.0.0`)
  - `FASTAPI_PORT` (дефолт: `8000`)
  - `CORS_ORIGINS` (дефолт: `"*"`)

## 6. Бэкенд: сервисы

### 6.1 `services/pdf_handler.py`
- `extract_text_and_coords(pdf_path)` — плоский текст + координаты слов/блоков через `page.get_text("words")` / `page.get_text("blocks")` (X, Y, ширина, высота).
- `render_page_to_png(pdf_path, page_number)` — рендер страницы в байты PNG для ИИ-отчета по странице.
- Ошибка `PdfHandlerError` при отсутствии текстового слоя (отсканированный PDF) — возвращать понятное уведомление, а не ложные совпадения.

### 6.2 `services/diff_engine.py`
- `compute_diff(text_a, text_b)` — diff через `diff-match-patch`.
- Левая панель (исходная версия): только `EQUAL` и `DELETE`. `DELETE` подсвечивается `<span class="bg-red-500/30 line-through">`.
- Правая панель (измененная версия): только `EQUAL` и `INSERT`. `INSERT` подсвечивается `<span class="bg-green-500/30">`.
- `INSERT` на левой панели и `DELETE` на правой панели **запрещены** (игнорируются).
- Возврат JSON с отдельными `left_panel` / `right_panel` (blocks + html) и координатами (`coords_left` / `coords_right`).

### 6.3 `services/vllm_client.py`
- `VllmClient` на базе `openai.AsyncOpenAI`, настроенный на эндпоинт vLLM из `config.settings`.
- `stream_analysis(prompt)` — потоковый текстовый ответ (SSE).
- `stream_analysis_with_image(system_prompt, image_base64, image_mime_type)` — потоковый визуальный анализ страницы (Qwen3-VL).
- При недоступности vLLM — выбрасывать `VllmClientError`, бэкенд возвращает HTTP 502 с понятной ошибкой; пользователь может продолжить работу с обычным diff.

### 6.4 `main.py`
- FastAPI-приложение с CORS (настройка из `CORS_ORIGINS`).
- Роуты (все относительные, готово к Nginx/Docker):
  - `GET /api/v1/health` — проверка работоспособности.
  - `POST /api/v1/compare` — прием двух PDF, вызов `pdf_handler` + `diff_engine`, возврат JSON_diff.
  - `POST /api/v1/analyze` — потоковый ИИ-анализ изменений (StreamingResponse / SSE).
  - `POST /api/v1/ai-report-page` — ИИ-отчет по странице: изображение + системный промпт → vLLM → потоковый ответ.
- Статика раздается из `static/` через `/static`.
- Нет жестко заданных хостов во фронтенд-запросах.

## 7. Фронтенд (`static/`)

### 7.1 `static/index.html`
- Два окна сравнения side-by-side (оригинал слева, новая версия справа).
- Сворачиваемая боковая панель "AI Аналитика".
- Подключение TailwindCSS через CDN и pdf.js через CDN.
- Относительные пути для всех AJAX-запросов (`/api/v1/...`).

### 7.2 `static/app.js`
- Загрузка двух PDF-файлов, отправка на `/api/v1/compare`.
- Рендер страниц через pdf.js в `<canvas>` (визуальная подложка).
- Прозрачный абсолютно позиционированный HTML-слой с текстовыми элементами (`<span class="diff-word">`) строго над своими координатами (PyMuPDF).
- Подсветка: удаленные (красный, зачеркивание) слева, добавленные (зеленый) справа.
- Умный синхронный скроллинг (lock-step) с привязкой к текстовым якорям (блокам), а не к пикселям.
- Боковая панель ИИ-аналитики со стримингом ответа (SSE).
- Кнопка "Сгенерировать ИИ-отчет по странице" — снимок текущей видимой области canvas → `/api/v1/ai-report-page` → vLLM.

### 7.3 `static/styles.css`
- Кастомные стили для diff-слоя, подсветки (`--diff-delete-bg`, `--diff-insert-bg`), компенсирующего пространства при замирании окна, полосы прокрутки, анимации вывода ИИ.

## 8. Требования к UI/UX (Git Split Diff + Side-by-Side Canvas)

- Нет конвертации PDF в Markdown. Отображение идет поверх оригинальной верстки страниц (pdf.js + `<canvas>`).
- Каждая страница PDF — полноценный графический объект (canvas).
- Координаты текстовых блоков/слов извлекаются бэкендом через PyMuPDF и передаются фронтенду.
- Синхронный скроллинг привязан к текстовым якорям. При добавленном блоке в Новом документе левое окно замирает (или показывает компенсирующее пустое пространство) до прохождения вставки.
- Боковая панель ИИ-аналитики с потоковым выводом и кнопкой отчета по странице с визуальным контекстом.

## 10. Правила ветвления и pull-request (обязательно для всего проекта)

**Это правило зафиксировано для всего проекта и не подлежит изменению без согласия команды.**

1. **Не коммитить напрямую в `main`.** Ветка `main` защищена — вливание в неё возможно только через pull-request.
2. **Каждое изменение — в новую ветку.** Создавайте отдельную ветку от `main` для каждой задачи/фичи/исправления (например, `feature/...`, `fix/...`, `chore/...`).
3. **Pull-request обязателен.** Перед вливанием в `main` необходимо создать pull-request из рабочей ветки в `main`.
4. **PR оформляется только на GitHub.** Локальное слияние ветки в `main` через `git merge` вместо GitHub PR запрещено. PR создаётся через GitHub веб-интерфейс (`github.com/<user>/file-compare-v2/pulls`) или GitHub CLI (`gh pr create`). Ревью, approbation и слияние проходят через GitHub (кнопка "Merge pull request").
5. **Вливание только после прохождения PR.** PR считается пройденным после проверки кода (code review) и успешного прохождения проверок (тесты, линтинг, сборка). Вливание в `main` допускается только после одобрения PR.
5. **Удаление побочной ветки.** После успешного вливания PR в `main` рабочая ветка **обязательно удаляется** (локально и на удалённом сервере).
6. **Имя ветки.** Используйте понятные имена: `feature/<задача>`, `fix/<задача>`, `docs/<задача>`, `chore/<задача>`.

7. **Тесты при любой правке кода.** При любом изменении исходного кода (`main.py`, `services/`, `static/app.js` и т.п.) необходимо добавить или обновить соответствующие тесты в папке `tests/` и убедиться, что все тесты зелёные (`pytest` проходит без ошибок), прежде чем создавать pull-request. Изменение без тестов не считается завершённым.

Пример рабочего процесса:
```bash
git checkout main
git pull origin main
git checkout -b feature/新功能
# ... изменения ...
git add -A
git commit -m "Описание изменений"
git push origin feature/новый-функционал
# Создать PR в main, пройти ревью и проверки
# После вливания:
git checkout main
git pull origin main
git branch -d feature/новый-функционал
git push origin --delete feature/новый-функционал
```

## 11. Планирование изменений (OpenSpec)

- Planning-артефакты хранятся в `openspec/changes/<имя-изменения>/`.
- Схема: `spec-driven` — `proposal.md` → `specs/<capability-path>/spec.md` → `design.md` → `tasks.md`.
- Спецификации описывают **WHAT** (поведение, требования, сценарии), а не реализацию.
- `design.md` описывает **HOW** (архитектура, решения, риски).
- `tasks.md` — чек-лист реализации с чекбоксами `- [ ]` / `- [x]`.

---

## 12. Проверка и приемка

- Приложение запускается через `uvicorn main:app` (с дефолтным конфигом без `.env`).
- `/api/v1/health` должен возвращать `{"status": "ok", ...}`.
- `/api/v1/compare` должен возвращать JSON с отдельными `left_panel` / `right_panel` и координатами.
- ИИ-маршруты (`/api/v1/analyze`, `/api/v1/ai-report-page`) требуют доступного vLLM endpoint; при недоступности — понятная ошибка HTTP 502.

## 13. Запреты

- Жестко заданные секреты/ключи в коде (все через `.env` + `config.py`).
- Прямые коммиты в `main`.
- Конвертация PDF в Markdown для отображения.
- Поддержка форматов, отличных от PDF (DOCX и т.п.) — не в объеме MVP.
- Аутентификация/авторизация — не в объеме MVP.
