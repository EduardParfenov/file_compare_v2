# file-compare-v2

Веб-приложение для гибридного сравнения двух версий PDF-документов:
визуальное сравнение в стиле Git Split Diff + ИИ-анализ изменений через
локальную VL-модель Qwen3-VL-8B (vLLM).

## Стек

- Бэкенд: Python 3.11, FastAPI (асинхронный), Uvicorn
- Обработка PDF: PyMuPDF (`fitz`)
- Алгоритм diff: Google `diff-match-patch`
- ИИ-анализ: асинхронный клиент `openai` к vLLM с потоковым ответом (StreamingResponse / SSE)
- Фронтенд: HTML5, TailwindCSS, Vanilla JavaScript, pdf.js (через CDN)

## Установка и запуск

### 1. Создать виртуальное окружение `.venv/`

**Windows (PowerShell):**

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
```

**Windows (CMD):**

```cmd
python -m venv .venv
.venv\Scripts\activate.bat
```

**Unix/macOS:**

```bash
python3 -m venv .venv
source .venv/bin/activate
```

### 2. Установить зависимости

```bash
pip install -r requirements.txt
```

Для разработки и запуска тестов дополнительно установите инструменты
разработки:

```bash
pip install -r requirements-dev.txt
```

### 3. Настроить переменные окружения

Скопируйте шаблон и заполните реальные значения:

```bash
cp .env.example .env
# отредактируйте .env, указав VLLM_API_URL, VLLM_API_KEY и т.д.
```

Файл `.env` с реальными секретами не попадает в Git (записан в `.gitignore`).
Если `.env` отсутствует, приложение использует значения по умолчанию из `config.py`.

**Приоритет источников:** встроенные значения по умолчанию < переменные
окружения оболочки < файл `.env`. Если переменная задана и в оболочке, и в
`.env` — используется значение из `.env`. Путь к `.env` определяется
относительно корня проекта, поэтому запуск из любого рабочего каталога
даёт одинаковую конфигурацию.

> **Важно для контейнеризации:** файл `.env` **не следует** встраивать в
> образ или копировать в контейнер: из-за приоритета над окружением оболочки
> он перекроет переменные, переданные оркестратором (`docker run -e ...`).
> Передавайте конфигурацию через окружение или монтируйте `.env` отдельно.

### 4. Запустить приложение

```bash
uvicorn main:app --reload
```

Приложение будет доступно по адресу `http://localhost:8000` — корневой маршрут
отдаёт пользовательский интерфейс (две панели сравнения и боковая панель
ИИ-аналитики).

Адрес прослушивания задаётся параметрами команды `uvicorn`
(`--host` / `--port`); значения `FASTAPI_HOST` / `FASTAPI_PORT` из `.env`
читаются приложением как настройки конфигурации, но адрес привязки ими
не определяется.

## Docker-совместимость

Код разработан так, чтобы быть готовым к контейнеризации (Docker) и работе
за реверс-прокси Nginx:
- все настройки берутся из `.env`;
- на фронтенде используются только относительные пути AJAX-запросов (`/api/v1/...`);
- статические файлы лежат в `static/`.

Dockerfile, docker-compose и конфиги Nginx добавляются отдельно (позже).

## Автоматические проверки (CI)

В репозитории настроен CI на GitHub Actions — workflow `.github/workflows/ci.yml`.
Он запускается:

- на каждый **pull request** (любой, независимо от ветки-источника);
- на каждый **push в `main`** — так подтверждается, что попавшее в основную ветку
  состояние действительно проходит проверку.

### Что делает проверка

1. Устанавливает Python 3.11 и зависимости из `requirements-dev.txt`
   (файл подключает `requirements.txt`; кэш pip — по нему же).
2. Устанавливает браузер Chromium для end-to-end теста фронтенда:
   `playwright install --with-deps chromium`.
3. Выполняет полный набор тестов командой `pytest`.

Проверка **не требует секретов**: файла `.env` в окружении CI нет, адрес
эндпоинта ИИ-модели не передаётся, ИИ-роуты проверяются моками. Набор тестов
одинаков локально и в CI — 59 тестов, включая браузерный end-to-end тест
(загрузка страницы, выбор двух PDF, запрос `/api/v1/compare`).

Полный прогон занимает порядка 3–4 минут: основное время — установка
зависимостей и браузера.

### Как запустить проверку локально

```bash
pip install -r requirements-dev.txt
python -m playwright install chromium   # нужен только для браузерного теста
pytest
```

Команда `pytest` работает из корня репозитория и не зависит от текущего
рабочего каталога: путь к корню проекта добавляется через `pythonpath` в
`pytest.ini`. Без браузера браузерный тест помечается как пропущенный, а не
как упавший.

### Как сделать проверку обязательной

Настройка хранится в репозитории на стороне GitHub, а не в коде, поэтому её
включает владелец репозитория вручную:

1. `Settings` → `Branches` → `Branch protection rules` → `Add rule`.
2. В поле «Branch name pattern» указать `main`.
3. Включить **Require status checks to pass before merging** и выбрать
   проверку `pytest`.
4. При необходимости включить **Require a pull request before merging** и
   **Require approvals**.

После этого pull request с красной проверкой нельзя слить кнопкой
«Merge pull request».

## Правила ветвления и Pull-Request (обязательно для всего проекта)

**Не коммитить напрямую в `main`.** Ветка `main` защищена — вливание в неё возможно
только через pull-request.

1. **Каждое изменение — в новую ветку** от `main` (`feature/...`, `fix/...`,
   `docs/...`, `chore/...`).
2. **Pull-request обязателен** перед вливанием в `main`.
3. **Вливание только после прохождения PR** (код-ревью и успешные проверки).
4. **После вливания PR побочная ветка удаляется** (локально и на удалённом сервере).

Пример рабочего процесса:

```bash
git checkout main
git pull origin main
git checkout -b feature/новая-задача
# ... изменения ...
git add -A
git commit -m "Описание изменений"
git push origin feature/новая-задача
# Создать PR в main, пройти ревью и проверки, влить
# После вливания:
git checkout main
git pull origin main
git branch -d feature/новая-задача
git push origin --delete feature/новая-задача
```

Подробные правила для агентов и разработчиков см. в `AGENTS.md`.
